⼀、项⽬调研

1.1 项⽬背景与价值

    Apache ShenYu 是异步、⾼性能、跨语⾔的 API ⽹关。请求进⼊⽹关后，会依次经过鉴权、限

流、路由和代理等插件，再由 Divide 插件选择后端服务实例。⽣产环境上线新版本时，通常不能

⼀次接收全部流量，因此需要先让少量⽤户访问新版本，观察稳定性后再逐步扩⼤范围，这就是

常说的“灰度发布”。在⽣产情况下，我们希望⽹关有能⼒让满⾜某⼀个条件的客户端，⽆论重复多

少次，都能尽量连接到同⼀个服务集群，然后再进⾏负载均衡，因为这样才能保证对于客户端的

体验来说⼤致是稳定的，不会出现抖动的情况，但是如今的 DividePlugin 的具体实现并没有做到这

⼀点，所以可能会导致同⼀个客户端本次连接到⽣产集群，下⼀次连接就连接到了灰度发布的集

群，这是需要我们完善的，因此有了本课题。

    本申请书把主要承载⽣产流量的版本称为 Stable（稳定版本），把正在⼩流量验证的新版本称

为 Canary（灰度版本）。项⽬⽬标不是发明⼀种新的负载均衡算法，⽽是在负载均衡之前增加“流
量分区”：先判断请求属于 Stable 还是 Canary，再从对应分区的健康实例中继续使⽤ ShenYu 原有

的轮询、随机或 Hash 算法。

1.2 需求分析

项⽬需要为 Divide Rule 增加独⽴的 Canary 配置：可按 Header、Cookie、Query、IP、租户或⽤户

等条件圈定灰度⼈群；在命中⼈群内按固定⽐例放量；⽤ Sticky Key 的稳定 Hash 保证同⼀⽤户在

⽐例不变时尽量落到同⼀分区；再通过 Upstream Labels 划分 Stable 与 Canary 实例。

还需处理⽬标分区⽆健康实例时的 STABLE 回退或 REJECT 拒绝策略，保证 Failover 重试继续使⽤

⾸次确定的分区；补齐 Admin/Dashboard 的配置与校验、请求量和回退次数等指标，并保持旧

gray=true/false 配置在未启⽤新版规则时⾏为不变。


1.3 当前调⽤链与主要问题

Selector/Rule → DividePlugin 读取 DivideRuleHandle → UpstreamCacheManager 获取健康实例 →

LoadbalancerUtils 选 择 实 例   → URIPlugin 构 造 地 址    → HTTP Client 转 发 ； 失 败 时

2.1 配置与数据结构设计

     拟在 DivideRuleHandle 中增加可为空的 CanaryConfig。canary == null 表⽰没有配置新版规则，

继续执⾏旧 gray 语义；canary 不为空但 enabled=false 时只⾛ Stable；enabled=true 时执⾏条件、⽐

    private CanaryConfig canary;

public final class CanaryConfig {

    private List<ConditionData> conditions;
    private Integer matchMode;            // AND / OR

    private StickyKey stickyKey;            // header/cookie/query/ip
    private Map<String, String> canaryLabels;
    private Map<String, String> stableLabels;
    private CanaryFallbackPolicy fallbackPolicy; // STABLE / REJECT
}

2.2 灰度分区

    灰度分区在负载均衡之前完成。对于灰度决策，我们可以认为，本项⽬的⽬标是相较于原来

的请求处理链，在取得路由上下⽂和选实例并转发之间加⼀个决定本请求 Stable / Canary 的流程。

我们把决定⼀个请求属于 Stable 还是 Canary 的服务抽象成 CanaryDecision 的组件，以下是字段定

义

public interface CanaryDecisionService {

    CanaryDecision decide(
        ServerWebExchange exchange,
        RuleData ruleData,
        CanaryConfig canaryConfig
    );
}

    其默认实现是

public class DefaultCanaryDecisionService
        implements CanaryDecisionService {
    // 条件匹配、获取 stickyKey、⼀致性哈希、百分⽐判断
}




    DefaultCanaryDecisionService 负 责 完 整 的 默 认 流 程 ： 先 复 ⽤      ConditionData 和

MatchStrategyFactory 判断请求是否属于灰度⼈群；conditions 为空时允许全部请求参加百分⽐分流，

条件未命中则进⼊ Stable。随后读取 Sticky Key，并⽤固定 Hash 算法和 Rule 级盐值计算 0 ⾄ 9999

的桶位，再与 percentage 对应的阈值⽐较。

    Sticky Key 可以来⾃ Header、Cookie、Query 或客户端 IP。缺少配置值时默认进⼊ Stable；

percentage 为 0 时所有命中请求进⼊ Stable，为 100 时所有命中请求进⼊ Canary。同⼀ Rule、同⼀

配置和同⼀ Sticky Key 得到稳定结果，⽐例变化时仅跨过新阈值的桶改变分区。

    DividePluginConfiguration 注册默认 CanaryDecisionService，并通过构造器注⼊ DividePlugin。

请求命中 Divide Rule 后，插件解析 DivideRuleHandle，调⽤决策服务，并把返回结果交给后续实例

过滤。分区结果在同⼀次请求中只计算⼀次，随后由 DividePlugin 写⼊ CanaryRouteContext，供转

发、重试和指标模块复⽤。

CanaryDecision decision = canaryDecisionService.decide(
        exchange,
        ruleData,
        divideRuleHandle.getCanary()
);

2.3 Divide 插件集成

    CanaryDecisionService 只回答请求属于哪个分区，CanaryUpstreamResolver 再把分区决定转换

成实际路由。这样可以把条件与⽐例计算、标签过滤、空池处理和具体实例负载均衡分开测试。

    调⽤顺序为：DividePlugin 先读取 DivideRuleHandle 和完整健康 Upstream。如果存在有效的

specify-domain，则继续使⽤ ShenYu 原有的指定节点逻辑并跳过⾃动分区；否则读取或计算

CanaryDecision，再进⼊标签过滤。

    CanaryUpstreamResolver 根据 Upstream.metadata 过滤候选实例。如果分区是 Canary，使⽤

canaryLabels，如果是 Stable， 使⽤ stableLabels；配置多个标签时，实例必须全部满⾜。标签匹配

只缩⼩健康候选池，不修改 UpstreamCacheManager 中的共享对象。

    若请求期望进⼊ Canary，但 Canary 池没有健康实例，fallbackPolicy=STABLE 时改⽤ Stable 池，

并 同 时 保 留         desiredPartition=canary 、 effectivePartition=stable 和   fallbackReason ；

fallbackPolicy=REJECT 时直接返回⽆可⽤ Upstream。Stable 池为空时默认拒绝，不⾃动切到

Canary。

    候选池确定后继续调⽤ LoadbalancerUtils.getForExchange，沿⽤ RoundRobin、Random 或

Hash 选择具体实例，不新增 Canary 专⽤负载均衡器。DefaultRetryStrategy 读取⾸次请求的

effectivePartition，在最新健康实例中重新过滤并排除失败节点，重试期间不重新计算 Percentage。

    当 DivideRuleHandle 中没有 CanaryConfig 时，DividePlugin 和 Upstream 数据处理链继续执⾏

旧 gray=true/false 的 独 占 池 ⾏ 为 ； 存 在 CanaryConfig 且 enabled=false 时 只 ⾛ Stable ； 只 有

enabled=true 时才启⽤条件、确定性分桶和 Labels 分区。

    以下是该组件的字段定义

public interface CanaryUpstreamResolver {

    CanaryUpstreamResult resolve(
        List<Upstream> healthyUpstreams,
        CanaryDecision decision,
        CanaryConfig config
    );
}

2.4 Admin 配置与同步

本部分负责解决两个问题：


  •   ⽤户如何在 Admin 中配置灰度规则和 Upstream 标签。
  •   配置修改后如何同步到⽹关并动态⽣效。


2.4.1 灰度规则配置

在 Divide 规则编辑页⾯中增加灰度发布配置，包括：


  •   是否启⽤灰度发布；
  •   灰度匹配条件及 AND/OR 匹配模式；
  •   灰度流量百分⽐；
  •   黏性标识来源，例如 Header、Cookie、Query；
  •   canary 和 stable 分区对应的标签；
  •   canary 节点不可⽤时的回退策略。




                                 6
这些配置最终作为 DivideRuleHandle 中的嵌套 canary 对象保存：

{
    "loadBalance": "roundRobin",
    "retry": 2,
    "canary": {
      "enabled": true,
      "percentage": 20,
      "stickyKey": {
         "paramType": "header",
         "paramName": "X-User-Id"
      },
      "canaryLabels": {
         "release": "canary"
      },
      "stableLabels": {
         "release": "stable"
      },
      "fallbackPolicy": "STABLE"
    }
}




Admin 保存时不需要为每个灰度字段增加单独的数据库列，⽽是继续使⽤现有的 rule.handle 字

段保存完整 JSON。

规则配置的同步链路为：

Admin 页⾯
    ↓
RuleDTO.handle
    ↓
RuleDO.handle 写⼊数据库
    ↓
RuleEventPublisher 发布配置变更
    ↓
WebSocket / HTTP / ZooKeeper 等同步通道
    ↓
RuleData.handle 到达⽹关
    ↓
DividePluginDataHandler 反序列化
    ↓
得到 DivideRuleHandle 并写⼊本地缓存

因此，在 DivideRuleHandle 中增加 CanaryConfig 后，可以继续复⽤ ShenYu 现有的规则同步

机制，不需要设计新的灰度配置同步协议。

2.4.2 Upstream 标签配置

在 Upstream 配置页⾯增加 labels 键值对输⼊能⼒，例如：

{
    "warmup": 10,
    "gray": false,
    "labels": {
      "release": "canary",
      "region": "cn-east"
    }
}

Upstream 标签优先存放在已有的 discovery_upstream.props 扩展字段中，并随

DiscoveryUpstreamData ⼀起同步。

同步链路为：

Admin 或服务注册
    ↓
DiscoveryUpstreamDTO.props
    ↓
discovery_upstream.props
    ↓
DiscoverySyncData
    ↓
配置同步通道
    ↓
DivideUpstreamDataHandler
    ↓
解析 labels 并构造 Upstream
    ↓
UpstreamCacheManager
⽹关端需要修改 DivideUpstreamDataHandler，将嵌套的 labels 解析为 Map<String,

String>，并保存到 Upstream.metadata 中，供 DividePlugin 进⾏分区过滤。

同时需要保证 Upstream 缓存更新时，gray 和 metadata 也能够随配置变化正确更新。

2.4.3 配置校验

Admin 保存配置前应进⾏基本校验：


     •   percentage 的取值范围为 0～100；
     •   配置百分⽐灰度时，stickyKey 必须能够确定参数类型和参数名称；
     •   canaryLabels 和 stableLabels 不应完全相同；
     •   fallbackPolicy 必须为系统⽀持的固定值；
     •   conditions 中的参数类型和匹配操作符必须有效。


对于不合法的配置，Admin 应在保存阶段返回明确的错误信息，避免错误配置同步到所有⽹关节

点。

2.5 指标与可观测性

灰度功能上线后，需要能够回答以下问题：


   •   当前有多少请求进⼊了 stable 和 canary？
   •   是否发⽣了 canary 回退 stable？
   •   两个分区的成功率和响应时间是否存在明显差异？
   •   某个请求为什么进⼊了当前分区？

三、实施⽅案

3.1 总体实施思路

    项⽬按“先确认数据契约，再实现纯决策组件，然后接⼊路由和重试，最后补齐管理端、指标

与⽂档”的顺序推进。每⼀步都先建⽴可独⽴运⾏的测试，再接⼊下⼀条链路，以便出现兼容问题

时能够快速定位和回滚。

    新 版 能 ⼒ 默 认 关 闭 。 规 则 没 有 CanaryConfig 时 ， ⽹ 关 继 续 执 ⾏ 旧 gray 逻 辑 ； 存 在

CanaryConfig 且 enabled=false 时只⾛ Stable；只有 enabled=true 时才启⽤新的条件匹配、确定性分

桶和标签分池。实现继续使⽤ ShenYu 现有 Java、Spring Boot、Spring WebFlux/Reactor、Gson 和

Metrics SPI，不引⼊新的分布式存储。


3.2 分阶段实施

    代码按可独⽴评审的⼩型 PR 提交。模型与兼容代码先于请求主链路合⼊，Divide 与重试改造

在稳定接⼜上开发，管理端和可观测性随后接⼊。每个 PR 同时提交对应测试，减少社区评审时的

上下⽂负担。

可运⾏测试环境。

3.2.2 配置模型与兼容解析

    在     shenyu-common 中 增 加        CanaryConfig 、 StickyKeyConfig 、 CanaryPartition 和

metadata，在 builder、缓存增量更新和防御性复制中完整传递，不再增加含义重复的字段。

    DivideUpstreamDataHandler 使⽤结构化 JSON 解析 nested labels，同时保留 warmup、gray、

healthCheckEnabled 等旧 Properties 标量字段。单个实例的 Props ⾮法时记录明确错误并隔离该条数

3.2.3 灰度分区决策

    实现 CanaryDecisionService 与 DefaultCanaryDecisionService。条件判断复⽤ ConditionData 和

MatchStrategyFactory；conditions 为空时允许纯百分⽐灰度，条件未命中或 Sticky Key 缺失时进⼊

Stable。

    百分⽐使⽤确定性 Hash 分桶，⽽不是每次随机选择。实现固定 Hash 算法、UTF-8 编码、Rule

级盐值和 0 ⾄ 9999 桶；同⼀ Rule、同⼀配置和同⼀ Sticky Key 得到相同分区。⽐例改变时，只有跨

过新阈值的桶改变分区。0% 全部进⼊ Stable，100% 的命中请求全部进⼊ Canary。

    ⾸次决策把          desiredPartition 、 effectivePartition 和   fallbackReason 保 存 到 不 可 变

CanaryRouteContext，并将实际分区写⼊ SHENYU_CANARY_PARTITION。后续重试和指标读取

该上下⽂，不重新计算分桶，也不复⽤负载均衡器⾃⼰的 Hash attribute。

3.2.4 Divide 插件与重试流程

    在 DividePluginConfiguration 中注册默认决策实现，通过构造器注⼊ DividePlugin，并增加

starter 装配测试。有效的 specify-domain 继续绕过⾃动分区；未命中时才获取完整健康 Upstream，

由 CanaryUpstreamResolver 按⽬标 Labels 全量匹配并处理 STABLE 或 REJECT 空池策略。

    候选池确定后继续调⽤ LoadbalancerUtils.getForExchange，RoundRobin、Random 和 Hash 只

负责从当前分区选择具体实例。处理 specify-domain 和标签过滤时创建候选列表或副本，不修改缓

存中的共享 Upstream 对象。

    DefaultRetryStrategy 不直接依赖 Divide 决策组件。Failover 时重新获取最新健康节点，读取

effectivePartition，排除已失败实例后仍在同⼀分区负载均衡；若⾸次发⽣ Canary 到 Stable 的回退，

则后续重试继续使⽤ Stable。分别为 CURRENT 和 FAILOVER 两种策略增加分区⼀致性测试。

3.2.5 Admin 动态同步与可观测性

    Rule 侧 继 续 使 ⽤ rule.handle 保 存 Canary 配 置 ， 经 RuleDTO.handle 、 RuleDO.handle 、

RuleEventPublisher 和现有同步通道下发为 RuleData.handle，再由 DividePluginDataHandler 更新⽹

关 缓 存 。 Upstream Labels 保 存 在 discovery_upstream.props ， 经 DiscoveryUpstreamData 、

DiscoverySyncData 和 DivideUpstreamDataHandler 写⼊ Upstream.metadata。

    Admin 和 Dashboard 增加字段校验、编辑与回显，保存时合并原 Props，避免覆盖未知扩展字

段。先保证配置可正确保存、同步和回读，再完善交互式表单。更新后通过多⽹关热更新测试验

证 Rule 与 Labels ⽆需重启即可⽣效。

    Divide 只把 selectorId、ruleId、desiredPartition、effectivePartition 和 fallbackReason 等有限上

下⽂写⼊ exchange。MetricsPlugin 在请求结束时结合最终 HTTP 状态上报分区请求量、回退次数和

分区请求耗时。指标使⽤固定枚举，不记录⽤户 ID、请求 ID、Sticky Key、Header、Cookie 或异常

原⽂。
