# 分布式事务技术方案

分布式事务的核心目标是：

> 保证一个业务操作跨越多个数据库、服务或消息中间件时，各参与方的数据能够保持一致。

常见分布式事务方案大致可以分为三类：

```text
分布式事务
├── 强一致性方案
│   ├── XA / 2PC
│   └── 3PC
│
├── 业务补偿方案
│   ├── AT
│   ├── TCC
│   └── Saga
│
└── 最终一致性方案
    ├── 本地消息表
    ├── 事务消息
    └── 普通消息队列 + 重试与补偿
```

不同方案在一致性、性能、可用性和业务侵入性之间存在明显差异。

---

## 一、基于协调提交的强一致性方案

强一致性方案的基本思想是：

> 所有事务参与者在最终提交之前，先由一个事务协调者统一询问和协调。只有所有参与者都同意提交，整个事务才提交；否则全部回滚。

典型方案包括：

- XA；
    
- 2PC；
    
- 3PC。
    

---

## 1. XA 协议

XA 是一种分布式事务标准规范，由事务管理器协调多个支持 XA 的资源管理器完成全局事务。

XA 中主要包含三个角色：

|角色|含义|
|---|---|
|AP|Application Program，应用程序|
|TM|Transaction Manager，事务管理器|
|RM|Resource Manager，资源管理器，例如 MySQL、Oracle|

结构如下：

```text
                     ┌──────────────────┐
                     │ 事务管理器 TM     │
                     └────────┬─────────┘
                              │
                  协调多个资源提交或回滚
                              │
             ┌────────────────┼────────────────┐
             ▼                ▼                ▼
       订单数据库 RM      库存数据库 RM      账户数据库 RM
```

应用程序不会分别决定各数据库事务是否提交，而是由事务管理器统一协调。

XA 协议通常采用两阶段提交，也就是 2PC。

### XA 的特点

优点：

- 数据一致性较强；
    
- 由数据库或事务管理器提供支持；
    
- 对业务代码侵入相对较小；
    
- 可以协调多个数据库事务。
    

缺点：

- 对数据库有要求，所有参与者必须支持 XA；
    
- 事务执行期间可能长时间占用数据库连接；
    
- 数据库锁持有时间较长；
    
- 性能和吞吐量较低；
    
- 事务协调器故障可能影响整个事务；
    
- 不适合高并发、长事务场景。
    

适用场景：

- 银行转账；
    
- 金融结算；
    
- 对强一致性要求很高的核心系统；
    
- 参与资源较少、事务时间较短的场景。
    

---

## 2. 两阶段提交 2PC

2PC 全称 Two-Phase Commit，即两阶段提交。

两阶段分别是：

```text
第一阶段：Prepare，准备阶段
第二阶段：Commit / Rollback，提交或回滚阶段
```

### 第一阶段：准备阶段

事务协调器向所有参与者发送 Prepare 请求。

每个参与者执行本地事务，但暂时不正式提交，而是：

1. 执行业务 SQL；
    
2. 写入事务日志；
    
3. 锁定相关资源；
    
4. 向协调器返回是否可以提交。
    

流程如下：

```text
事务协调器
     │
     ├── Prepare ──► 订单数据库
     ├── Prepare ──► 库存数据库
     └── Prepare ──► 账户数据库
                         │
                         ▼
                 执行本地事务但不提交
```

参与者返回：

```text
YES：本地事务执行成功，可以提交
NO：本地事务执行失败，不能提交
```

### 第二阶段：提交或回滚阶段

协调器根据第一阶段的结果做出决定。

如果所有参与者都返回 YES：

```text
所有 Prepare 成功
        │
        ▼
协调器发送 Commit
        │
        ├──► 订单数据库提交
        ├──► 库存数据库提交
        └──► 账户数据库提交
```

如果任意参与者返回 NO：

```text
存在 Prepare 失败
        │
        ▼
协调器发送 Rollback
        │
        ├──► 订单数据库回滚
        ├──► 库存数据库回滚
        └──► 账户数据库回滚
```

完整流程：

```text
开始全局事务
      │
      ▼
协调器发送 Prepare
      │
      ▼
所有参与者准备成功？
   ┌──┴──┐
   │     │
  是     否
   │     │
   ▼     ▼
Commit  Rollback
   │     │
   ▼     ▼
全部提交 全部回滚
```

### 2PC 存在的问题

#### 1. 同步阻塞

第一阶段执行成功后，参与者需要持续持有数据库锁，等待协调器发送第二阶段指令。

```text
Prepare 成功
    │
    ▼
锁住数据库资源
    │
    ▼
等待 Commit 或 Rollback
```

等待期间，其他事务可能无法访问这些数据。

#### 2. 协调器单点故障

如果参与者已经完成 Prepare，但协调器宕机：

```text
参与者已经准备完成
        │
        ▼
协调器宕机
        │
        ▼
参与者不知道应该提交还是回滚
```

参与者可能长期处于阻塞状态。

#### 3. 数据不一致风险

协调器发送 Commit 时，如果部分参与者收到指令，部分参与者没有收到：

```text
订单数据库：Commit 成功
库存数据库：Commit 成功
账户数据库：没有收到 Commit
```

仍然可能产生短暂甚至长期的数据不一致。

#### 4. 性能较低

2PC 需要至少两轮网络通信，并且会长时间占用事务资源，因此不适合高并发互联网业务。

---

## 3. 三阶段提交 3PC

3PC 全称 Three-Phase Commit，即三阶段提交。

它在 2PC 的 Prepare 和 Commit 之间增加了一个预提交阶段。

三个阶段分别是：

```text
第一阶段：CanCommit
第二阶段：PreCommit
第三阶段：DoCommit
```

### 第一阶段：CanCommit

协调器询问所有参与者是否具备执行事务的条件。

此阶段通常只进行检查，不真正执行事务。

```text
协调器
   │
   ├── CanCommit? ──► 订单数据库
   ├── CanCommit? ──► 库存数据库
   └── CanCommit? ──► 账户数据库
```

参与者根据自身状态返回：

```text
YES：可以执行
NO：不能执行
```

### 第二阶段：PreCommit

如果所有参与者都返回 YES，协调器发送 PreCommit。

参与者执行本地事务，记录日志并锁定资源，但暂不正式提交。

```text
所有 CanCommit 成功
        │
        ▼
发送 PreCommit
        │
        ▼
参与者执行事务并进入预提交状态
```

如果存在参与者返回 NO，则协调器通知所有参与者中止事务。

### 第三阶段：DoCommit

如果所有参与者的 PreCommit 都成功，协调器发送 DoCommit，参与者正式提交事务。

```text
所有 PreCommit 成功
         │
         ▼
发送 DoCommit
         │
         ▼
参与者正式提交
```

完整流程：

```text
CanCommit
    │
    ▼
所有参与者可以执行？
 ┌──┴──┐
 │     │
是     否
 │     │
 ▼     ▼
PreCommit  Abort
    │
    ▼
所有预提交成功？
 ┌──┴──┐
 │     │
是     否
 │     │
 ▼     ▼
DoCommit  Abort
```

### 3PC 对 2PC 的改进

3PC 主要增加了：

- 超时机制；
    
- 预提交状态；
    
- 参与者在部分场景下可以根据自身状态进行决策。
    

与 2PC 相比，3PC 可以在一定程度上降低参与者长期阻塞的问题。

### 3PC 的问题

3PC 并没有彻底解决分布式事务问题：

- 网络通信次数更多；
    
- 整体性能更低；
    
- 实现复杂；
    
- 网络分区时仍然可能产生数据不一致；
    
- 实际工程中使用较少。
    

因此，大多数实际系统使用 XA/2PC，或者采用 TCC、Saga、事务消息等业务级方案，而不是直接使用 3PC。

# 二、基于业务补偿的分布式事务方案

业务补偿方案不会完全依赖数据库原生事务，而是通过：

- 全局事务协调；
    
- 业务状态控制；
    
- 反向补偿操作；
    
- 重试和幂等；
    

保证多个本地事务之间的一致性。

常见方案包括：

- AT；
    
- TCC；
    
- Saga。
    

---

## 1. AT 模式

AT 是 Automatic Transaction，自动事务模式，常见于 Seata 等分布式事务框架。

AT 模式同样采用两阶段思想，但与 XA 不同：

> XA 第一阶段执行后不提交本地事务，而 AT 第一阶段会直接提交本地事务，并通过 Undo Log 保存回滚数据。

AT 模式主要角色包括：

|角色|含义|
|---|---|
|TC|Transaction Coordinator，全局事务协调器|
|TM|Transaction Manager，全局事务发起者|
|RM|Resource Manager，分支事务参与者|

### AT 第一阶段

第一阶段执行本地业务 SQL，并记录数据修改前后的镜像。

例如执行：

```sql
UPDATE account
SET balance = balance - 100
WHERE user_id = 1;
```

AT 会记录：

```text
修改前镜像：balance = 1000
修改后镜像：balance = 900
```

然后：

1. 执行业务 SQL；
    
2. 写入 Undo Log；
    
3. 注册分支事务；
    
4. 提交本地事务；
    
5. 释放数据库本地锁。
    

流程如下：

```text
执行业务 SQL
     │
     ▼
记录前镜像和后镜像
     │
     ▼
写入 Undo Log
     │
     ▼
提交本地事务
     │
     ▼
向 TC 报告分支成功
```

虽然本地事务已经提交，但全局事务还没有结束。

为了防止其他全局事务修改相同数据，AT 会维护全局锁。

### AT 第二阶段提交

如果所有分支事务都成功：

```text
全局事务成功
      │
      ▼
异步删除 Undo Log
      │
      ▼
释放全局锁
```

由于第一阶段本地事务已经提交，所以第二阶段提交非常轻量，主要进行清理工作。

### AT 第二阶段回滚

如果全局事务失败：

```text
全局事务失败
      │
      ▼
读取 Undo Log
      │
      ▼
校验当前数据是否仍等于后镜像
      │
      ├── 是 ──► 根据前镜像恢复数据
      │
      └── 否 ──► 出现脏写冲突，需要人工或异常处理
```

例如：

```text
修改前：1000
修改后：900
```

回滚时将余额从 900 恢复为 1000。

### AT 的优点

- 对业务代码侵入较小；
    
- 通常只需要添加全局事务注解；
    
- 第二阶段提交速度较快；
    
- 适合传统关系型数据库业务；
    
- 开发成本低于 TCC。
    

### AT 的缺点

- 依赖关系型数据库；
    
- 通常要求 SQL 可以被框架正确解析；
    
- 需要代理数据源；
    
- 依赖 Undo Log 和全局锁；
    
- 热点数据容易产生全局锁竞争；
    
- 不适合长事务；
    
- 回滚依赖数据前后镜像；
    
- 对跨数据库、跨中间件能力有一定限制。
    

### AT 适用场景

- 普通订单业务；
    
- 多个微服务分别操作关系型数据库；
    
- 业务允许框架自动生成补偿；
    
- 希望降低业务代码改造成本的场景。
    

---

## 2. TCC 模式

TCC 分为三个阶段：

```text
Try
Confirm
Cancel
```

TCC 不依赖数据库自动回滚，而是要求业务系统自行实现资源预留、确认和取消逻辑。

### Try 阶段

Try 阶段负责：

- 检查业务条件；
    
- 预留业务资源；
    
- 冻结资金或库存；
    
- 不直接完成最终业务操作。
    

例如用户有 1000 元，需要支付 100 元：

```text
可用余额：1000 → 900
冻结余额：0 → 100
```

此时资金只是被冻结，还没有正式扣除。

### Confirm 阶段

如果所有参与者的 Try 都成功，则执行 Confirm。

```text
冻结余额：100 → 0
实际完成扣款
```

Confirm 应设计为：

- 幂等；
    
- 尽量不失败；
    
- 不再进行复杂业务校验；
    
- 只使用 Try 阶段预留的资源。
    

### Cancel 阶段

如果任意参与者 Try 失败，则执行 Cancel。

```text
可用余额：900 → 1000
冻结余额：100 → 0
```

完整流程：

```text
开始全局事务
      │
      ▼
执行所有 Try
      │
      ▼
所有 Try 成功？
   ┌──┴──┐
   │     │
  是     否
   │     │
   ▼     ▼
Confirm Cancel
   │     │
   ▼     ▼
正式提交 释放预留资源
```

### TCC 必须解决的问题

#### 1. 幂等问题

Confirm 和 Cancel 可能因为网络超时被重复调用。

```text
第一次 Confirm 成功，但响应丢失
           │
           ▼
协调器再次调用 Confirm
```

因此 Confirm 和 Cancel 必须保证多次执行结果一致。

#### 2. 空回滚

Try 请求还没有到达参与者，但 Cancel 请求先到达。

```text
Try 未执行
   │
   ▼
Cancel 到达
```

此时 Cancel 不能错误地释放不存在的资源，而应该识别这是一次空回滚。

#### 3. 事务悬挂

Cancel 已经执行完成，但延迟的 Try 请求之后才到达。

```text
Cancel 已执行
      │
      ▼
延迟的 Try 又到达
```

如果仍然执行 Try，就会导致资源被重新冻结。

因此参与者需要记录事务状态，防止 Cancel 后再次执行 Try。

### TCC 的优点

- 一致性较强；
    
- 不依赖数据库 XA；
    
- 可以跨数据库、缓存、消息中间件；
    
- 性能通常优于 XA；
    
- 锁定的是业务资源，而不是数据库长事务锁；
    
- 适合核心资金和库存业务。
    

### TCC 的缺点

- 对业务侵入非常大；
    
- 每个操作都需要编写 Try、Confirm、Cancel；
    
- 开发和维护成本高；
    
- 必须处理幂等、空回滚和悬挂；
    
- 补偿逻辑复杂；
    
- 业务模型必须支持资源预留。
    

### TCC 适用场景

- 支付扣款；
    
- 库存预占；
    
- 红包冻结；
    
- 优惠券锁定；
    
- 对一致性要求较高的核心业务。

## 3. Saga 模式

Saga 适用于长事务场景。

它将一个全局事务拆分为多个可以独立提交的本地事务。

假设全局事务包含：

```text
T1：创建订单
T2：扣减库存
T3：扣减余额
T4：增加积分
```

每一个本地事务都对应一个补偿操作：

```text
T1 创建订单  ──► C1 取消订单
T2 扣减库存  ──► C2 恢复库存
T3 扣减余额  ──► C3 退还余额
T4 增加积分  ──► C4 扣回积分
```

正常执行：

```text
T1 → T2 → T3 → T4 → 完成
```

如果执行 T3 时失败：

```text
T1 成功
   │
   ▼
T2 成功
   │
   ▼
T3 失败
   │
   ▼
执行 C2 恢复库存
   │
   ▼
执行 C1 取消订单
```

完整流程：

```text
T1 创建订单
   │
   ├──失败──► 结束
   │
   ▼
T2 扣减库存
   │
   ├──失败──► C1 取消订单
   │
   ▼
T3 扣减余额
   │
   ├──失败──► C2 恢复库存 ──► C1 取消订单
   │
   ▼
T4 增加积分
   │
   ├──失败──► C3 退余额 ──► C2 恢复库存 ──► C1 取消订单
   │
   ▼
事务完成
```

Saga 主要有两种实现方式。

### 编排式 Saga

由一个统一的 Saga 协调器控制所有步骤。

```text
Saga 协调器
    │
    ├──► 订单服务
    ├──► 库存服务
    ├──► 支付服务
    └──► 积分服务
```

优点：

- 流程清晰；
    
- 容易追踪事务状态；
    
- 补偿顺序明确。
    

缺点：

- 协调器逻辑复杂；
    
- 可能形成中心化依赖。
    

### 编舞式 Saga

各服务通过消息事件驱动下一个服务。

```text
订单创建事件
      │
      ▼
库存服务扣库存
      │
      ▼
发布库存已扣减事件
      │
      ▼
支付服务扣款
```

如果失败，则发布补偿事件。

优点：

- 服务之间耦合较低；
    
- 没有集中式流程控制器；
    
- 扩展性较好。
    

缺点：

- 整体流程不直观；
    
- 事件链较长时难以排查；
    
- 容易形成事件风暴；
    
- 补偿顺序管理困难。
    

### Saga 的优点

- 适合长事务；
    
- 不会长时间持有数据库锁；
    
- 各步骤都是独立本地事务；
    
- 吞吐量和可用性较高；
    
- 适合复杂业务流程。
    

### Saga 的缺点

- 只能保证最终一致性；
    
- 中间状态对其他服务可见；
    
- 补偿操作可能失败；
    
- 不是所有操作都可以补偿；
    
- 补偿不一定能完全恢复原始状态。
    

例如：

```text
短信已经发送
```

无法真正撤回短信，只能再发送一条更正通知。

### Saga 适用场景

- 订单履约；
    
- 旅游预订；
    
- 物流流程；
    
- 跨多个服务的长业务流程；
    
- 可以接受短时间数据不一致的场景。

# 三、基于消息的最终一致性方案

基于消息的最终一致性方案并不要求所有服务在同一时刻完成事务。

它允许系统短时间不一致，通过：

- 可靠消息；
    
- 消息重试；
    
- 消费幂等；
    
- 定时补偿；
    
- 数据对账；
    

保证数据最终达到一致状态。

常见方案包括：

- 本地消息表；
    
- 事务消息；
    
- 普通消息队列配合重试和补偿。
    

---

## 1. 本地消息表

本地消息表的核心思想是：

> 业务数据和待发送消息写入同一个数据库事务，从而保证业务操作和消息记录不会出现一个成功、一个失败。

例如创建订单后需要通知库存服务扣减库存。

数据库中增加一张消息表：

```text
order
local_message
```

业务代码：

```java
@Transactional
public void createOrder() {
    orderMapper.insertOrder();
    messageMapper.insertMessage();
}
```

本地事务可以保证：

```text
订单写入成功，消息记录也成功
或者
订单和消息记录都失败
```

后台任务不断扫描未发送消息：

```text
扫描 local_message
       │
       ▼
查询未发送消息
       │
       ▼
发送到消息队列
       │
       ├──失败──► 保持未发送状态 ──► 稍后重试
       │
       ▼
标记为已发送
```

完整流程：

```text
开始本地事务
      │
      ├── 写入订单表
      └── 写入消息表
      │
      ▼
提交本地事务
      │
      ▼
后台任务扫描消息表
      │
      ▼
发送 MQ 消息
      │
      ├──失败──► 下次继续发送
      │
      ▼
消费者处理业务
      │
      ├──失败──► MQ 重试
      │
      ▼
最终一致
```

### 消息重复问题

假设消息已经成功发送，但生产者在更新消息状态前宕机：

```text
消息发送成功
      │
      ▼
应用宕机
      │
      ▼
消息表仍然是未发送
      │
      ▼
后台任务再次发送
```

因此消费者必须保证幂等。

常见幂等方式：

- 业务唯一键；
    
- 数据库唯一索引；
    
- 消费记录表；
    
- Redis 去重；
    
- 状态机控制。
    

### 本地消息表的优点

- 实现原理简单；
    
- 不依赖消息队列的事务能力；
    
- 业务数据与消息记录强一致；
    
- 可以通过重试保证消息最终发送。
    

### 本地消息表的缺点

- 侵入业务数据库；
    
- 需要维护消息表；
    
- 需要定时扫描任务；
    
- 消息量大时会给数据库带来压力；
    
- 需要清理历史消息；
    
- 存在重复消息，需要消费幂等。
    

### 本地消息表适用场景

- 对消息可靠性要求较高；
    
- 消息队列不支持事务消息；
    
- 业务量中等；
    
- 可以接受最终一致性的场景。
    

---

## 2. 事务消息

事务消息由消息中间件直接提供，例如 RocketMQ 事务消息。

事务消息的核心目标是解决：

```text
本地数据库事务
        +
消息发送
```

之间的一致性问题。

事务消息通常分为以下步骤：

```text
1. 发送半消息
2. 执行本地事务
3. 提交或回滚消息
4. 必要时进行事务状态回查
```

### 第一步：发送半消息

生产者先发送一条半消息。

```text
生产者 ──► 消息队列
```

半消息已经存储在 Broker 中，但消费者暂时看不到。

### 第二步：执行本地事务

半消息发送成功后，生产者执行本地数据库事务。

```text
发送半消息成功
       │
       ▼
执行本地事务
       │
       ├──成功
       └──失败
```

### 第三步：提交或回滚消息

如果本地事务成功：

```text
向 MQ 提交 Commit
        │
        ▼
消息对消费者可见
```

如果本地事务失败：

```text
向 MQ 提交 Rollback
        │
        ▼
消息被丢弃
```

### 第四步：事务回查

如果本地事务已经执行，但生产者在提交消息状态前宕机：

```text
本地事务执行完成
       │
       ▼
生产者宕机
       │
       ▼
MQ 不知道应该 Commit 还是 Rollback
```

消息队列会主动回查生产者的本地事务状态：

```text
RocketMQ
   │
   └── 查询本地事务状态 ──► 生产者
                              │
                              ├── 已成功：Commit
                              ├── 已失败：Rollback
                              └── 未知：稍后继续回查
```

完整流程：

```text
发送半消息
     │
     ├──失败──► 结束，本地事务不执行
     │
     ▼
执行本地事务
     │
  ┌──┴──┐
  │     │
成功    失败
  │     │
  ▼     ▼
Commit Rollback
  │
  ▼
消费者收到消息
  │
  ▼
执行下游业务
  │
  ├──失败──► 重试
  │
  ▼
最终一致
```

### 事务消息的优点

- 不需要自己维护本地消息表；
    
- 减少数据库轮询；
    
- 消息队列提供事务状态回查；
    
- 可靠性较高；
    
- 适合高并发场景。
    

### 事务消息的缺点

- 依赖特定消息中间件；
    
- 只能保证生产者本地事务与消息发送的一致性；
    
- 无法自动保证消费者业务一定成功；
    
- 消费者仍然需要重试和幂等；
    
- 本地事务状态查询逻辑需要可靠实现。
    

### 事务消息适用场景

- 创建订单后异步扣库存；
    
- 支付成功后异步更新订单；
    
- 用户注册后发送初始化任务；
    
- 数据库事务与 RocketMQ 消息需要保持一致的场景。

## 3. 普通消息队列

普通消息队列方案通过事件驱动，使不同服务分别完成自己的本地事务。

例如订单创建成功后发送扣库存消息：

```text
订单服务
   │
   ├── 创建订单
   │
   └── 发送扣库存消息
           │
           ▼
        RocketMQ
           │
           ▼
        库存服务
           │
           └── 扣减库存
```

消息队列本身可以提供：

- 消息持久化；
    
- 消费失败重试；
    
- 死信队列；
    
- 顺序消费；
    
- 延迟消息。
    

但是普通消息队列不能天然保证：

```text
数据库提交成功
        +
消息一定发送成功
```

例如：

```text
数据库订单写入成功
        │
        ▼
应用发送消息前宕机
        │
        ▼
库存服务永远收不到消息
```

因此普通 MQ 通常需要与以下机制组合：

- 本地消息表；
    
- Outbox Pattern；
    
- 事务消息；
    
- 定时补偿任务；
    
- 数据对账；
    
- Binlog/CDC 投递消息。
    

### 消费者处理流程

```text
收到消息
   │
   ▼
检查是否已经消费？
   │
   ├── 是 ──► 直接返回成功
   │
   └── 否
        │
        ▼
     执行业务
        │
        ├── 成功 ──► 记录消费状态
        │
        └── 失败 ──► 抛出异常，等待 MQ 重试
```

### 普通消息队列的优点

- 服务之间解耦；
    
- 吞吐量高；
    
- 可以削峰填谷；
    
- 不会长时间阻塞主业务；
    
- 适合异步化和最终一致性。
    

### 普通消息队列的缺点

- 无法单独解决数据库与消息发送的一致性；
    
- 消息可能重复；
    
- 消息可能延迟；
    
- 消费可能失败；
    
- 需要幂等、重试、死信和补偿机制；
    
- 系统短时间内可能处于不一致状态。
    

### 普通消息队列适用场景

- 积分增加；
    
- 邮件和短信通知；
    
- 搜索索引更新；
    
- 缓存刷新；
    
- 日志和数据同步；
    
- 对实时强一致要求不高的业务。

# 四、本地消息表、事务消息和普通 MQ 的区别

|对比项|本地消息表|事务消息|普通 MQ|
|---|---|---|---|
|业务数据与消息一致性|通过本地数据库事务保证|通过半消息和事务回查保证|默认无法保证|
|是否需要消息表|需要|不需要|通常不需要|
|是否需要定时扫描|需要|不需要|不需要|
|是否依赖特定 MQ|否|是|否|
|是否可能重复消息|是|是|是|
|消费端是否需要幂等|需要|需要|需要|
|一致性模型|最终一致性|最终一致性|最终一致性|
|实现复杂度|中等|中等|单独使用简单，但可靠性方案复杂|

三种方案都不能省略消费者幂等。

因为在分布式系统中：

> 可靠消息通常只能做到至少投递一次，而不是严格只投递一次。

# 五、各分布式事务方案对比

|方案|一致性|性能|业务侵入|是否长时间持锁|适用场景|
|---|---|--:|--:|--:|---|
|XA / 2PC|强一致性|较低|较低|是|金融、跨数据库强一致|
|3PC|较强一致性|很低|较低|有所缓解|理论研究较多，实际较少|
|AT|较强一致性|中等|较低|使用全局锁|普通关系型数据库微服务|
|TCC|较强一致性|较高|很高|业务资源预留|资金、库存等核心业务|
|Saga|最终一致性|较高|较高|否|长事务、复杂业务流程|
|本地消息表|最终一致性|中等|中等|否|可靠事件投递|
|事务消息|最终一致性|较高|中等|否|数据库事务与 MQ 一致|
|普通 MQ|最终一致性|高|较低|否|非核心异步业务|

# 六、方案选择原则

选择分布式事务方案时，需要先判断业务是否真的需要强一致性。

```text
业务是否允许短时间不一致？
          │
      ┌───┴───┐
      │       │
     不允许    允许
      │       │
      ▼       ▼
强一致性方案   最终一致性方案
      │       │
      ▼       ▼
XA / AT / TCC  Saga / 本地消息表 / 事务消息 / MQ
```

## 强一致性场景

适合：

- 资金扣减；
    
- 账户转账；
    
- 核心库存；
    
- 证券交易；
    
- 不允许出现中间状态的业务。
    

可以考虑：

```text
XA / 2PC
AT
TCC
```

其中：

- 数据库支持 XA、并发量不高：考虑 XA；
    
- 关系型数据库、希望减少代码改造：考虑 AT；
    
- 核心业务、可以设计冻结资源：考虑 TCC。
    

## 最终一致性场景

适合：

- 增加积分；
    
- 发送通知；
    
- 更新搜索索引；
    
- 更新缓存；
    
- 数据统计；
    
- 订单状态同步。
    

可以考虑：

```text
Saga
本地消息表
事务消息
普通 MQ + 重试补偿
```

# 七、分布式事务的共同基础能力

无论采用哪种分布式事务方案，都需要考虑以下问题。

## 1. 幂等

同一个请求可能被多次执行，但业务结果只能生效一次。

```text
第一次请求：执行成功，但响应丢失
                │
                ▼
调用方重新请求
                │
                ▼
服务端必须识别重复请求
```

常见实现：

- 业务唯一键；
    
- 数据库唯一索引；
    
- 状态机；
    
- Redis 去重；
    
- 消费记录表；
    
- 全局事务 ID。
    

## 2. 重试

网络超时不代表业务一定失败，因此失败操作通常需要重试。

重试必须与幂等结合，否则可能重复扣款、重复扣库存。

## 3. 补偿

已经提交的本地事务无法直接由其他服务回滚，只能执行反向业务操作。

```text
扣库存：库存 - 1
补偿：库存 + 1
```

## 4. 状态机

业务状态必须限制合法流转。

例如：

```text
待支付 → 已支付 → 已完成
   │
   └────► 已取消
```

不允许：

```text
已完成 → 待支付
```

## 5. 超时处理

远程调用超时时，不能直接认为对方没有执行。

应通过：

- 查询接口；
    
- 事务状态表；
    
- 消息回查；
    
- 定时对账；
    

确认最终结果。

## 6. 对账和人工补偿

任何自动分布式事务方案都无法保证所有极端故障百分之百自动恢复。

核心业务通常还需要：

```text
定时对账
   │
   ▼
发现异常数据
   │
   ▼
自动补偿
   │
   ├──成功──► 恢复一致
   │
   └──失败──► 进入人工处理
```

# 八、总结

各种分布式事务方案本质上是在一致性、可用性、性能和开发成本之间做权衡。

```text
XA / 2PC：
依赖事务协调器统一提交，强一致性较高，但性能较低。

3PC：
在 2PC 基础上增加预提交和超时机制，但实现复杂，实际使用较少。

AT：
框架自动记录 Undo Log 并进行数据补偿，业务侵入较低。

TCC：
业务自行实现 Try、Confirm、Cancel，一致性较强，但开发成本高。

Saga：
将长事务拆成多个本地事务，通过反向操作进行补偿。

本地消息表：
业务数据和消息记录在同一个本地事务中，再异步发送消息。

事务消息：
通过半消息、本地事务和事务回查，保证本地事务与消息发送一致。

普通消息队列：
通过重试、幂等、死信和补偿实现最终一致性，但不能单独解决数据库与消息发送的一致性。
```

一句话概括：

> 强一致性方案通过“提交前统一协调”保证一致，补偿型方案通过“失败后执行反向操作”恢复一致，消息型方案通过“可靠投递、重试和幂等”实现最终一致。
