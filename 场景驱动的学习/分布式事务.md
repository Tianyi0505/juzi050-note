在单体应用中，一个业务操作通常只涉及一个数据库，可以通过本地事务保证数据一致性。

进入微服务架构后，一个业务可能跨越多个服务和数据库。例如创建订单时，需要完成：

```text
订单服务：创建订单
库存服务：扣减库存
账户服务：完成支付
积分服务：增加积分
```

每个服务只能管理自己的本地事务，无法直接回滚其他服务已经提交的数据。因此，需要通过分布式事务协调多个本地事务。

常见方案可以分为三类：

```text
分布式事务
│
├── 协调提交
│   ├── XA / 2PC
│   └── 3PC
│
├── 业务补偿
│   ├── AT
│   ├── TCC
│   └── Saga
│
└── 可靠消息
    ├── 本地消息表
    ├── 事务消息
    └── MQ + 重试与补偿
```

不同方案主要在一致性、性能、可用性和业务侵入性之间进行取舍。

---

# 一、XA / 2PC

XA 是分布式事务规范，定义了事务管理器和多个资源管理器之间的协作方式。

XA 事务通常通过两阶段提交，也就是 2PC 完成。

## 1. Prepare 阶段

事务协调器向所有参与者发送 Prepare 请求。

参与者会执行本地事务、写入事务日志并锁定资源，但暂时不会提交。

```text
协调器发送 Prepare
      │
      ▼
参与者执行业务 SQL
      │
      ▼
写入事务日志并锁定资源
      │
      ▼
返回是否可以提交
```

## 2. Commit 或 Rollback 阶段

协调器根据所有参与者的执行结果决定提交还是回滚。

```text
所有参与者都 Prepare 成功？
      │
      ├── 否 ─────────► Rollback
      │
      └── 是
          │
          ▼
        Commit
```

2PC 可以提供较强的原子提交能力，但 Prepare 成功后，参与者需要持续持有数据库锁。如果协调器故障或网络异常，事务资源可能长时间无法释放。

因此，XA / 2PC 更适合：

- 参与资源较少；
    
- 事务执行时间较短；
    
- 数据库支持 XA；
    
- 对统一提交或回滚要求较高的场景。
    

---

# 二、3PC

3PC 在 2PC 的基础上增加了预提交阶段：

```text
CanCommit
    │
    ▼
PreCommit
    │
    ▼
DoCommit
```

完整流程如下：

```text
CanCommit
    │
    ▼
全部参与者都可以执行？
    │
    ├── 否 ─────────► Abort
    │
    └── 是
        │
        ▼
    PreCommit
        │
        ▼
全部参与者都预提交成功？
        │
        ├── 否 ─────► Abort
        │
        └── 是
            │
            ▼
        DoCommit
```

3PC 通过超时机制和预提交状态，降低参与者长期阻塞的概率。

但它增加了网络通信和状态管理成本，在网络分区下仍然可能出现数据不一致，因此实际业务中使用较少。

---

# 三、AT 模式

AT 是 Seata 中常见的分布式事务模式。

AT 同样分为两个阶段，但它与 XA / 2PC 的区别是：

> XA 第一阶段执行后暂不提交，AT 第一阶段会直接提交本地事务，并通过 Undo Log 保存回滚数据。

## 1. 第一阶段

假设执行：

```sql
UPDATE account
SET balance = balance - 100
WHERE user_id = 1;
```

AT 会记录数据修改前后的镜像：

```text
前镜像：balance = 1000
后镜像：balance = 900
```

执行流程如下：

```text
执行业务 SQL
      │
      ▼
记录前镜像和后镜像
      │
      ▼
写入 Undo Log
      │
      ▼
提交本地事务
      │
      ▼
向协调器报告结果
```

本地事务提交后会释放数据库本地锁，但 AT 会通过全局锁控制多个全局事务之间的数据冲突。

## 2. 第二阶段

全局事务成功时，异步删除 Undo Log。

全局事务失败时，根据 Undo Log 恢复修改前的数据：

```text
读取 Undo Log
      │
      ▼
当前数据是否等于后镜像？
      │
      ├── 否 ─────────► 数据冲突，进入异常处理
      │
      └── 是
          │
          ▼
      恢复前镜像
```

AT 的业务侵入较低，适合多个服务操作关系型数据库的普通业务。

它依赖代理数据源、Undo Log、SQL 解析和全局锁，不适合长事务以及热点数据竞争严重的场景。

---

# 四、TCC 模式

TCC 将一个业务操作拆分为三个阶段：

```text
Try
Confirm
Cancel
```

## 1. Try

Try 阶段检查业务条件并预留资源。

例如冻结 100 元：

```text
可用余额：1000 → 900
冻结余额：0 → 100
```

## 2. Confirm

所有参与者的 Try 都成功后，执行 Confirm，正式使用预留资源。

```text
冻结余额：100 → 0
完成实际扣款
```

## 3. Cancel

任意参与者 Try 失败时，执行 Cancel，释放已经预留的资源。

```text
冻结余额：100 → 0
可用余额：900 → 1000
```

完整流程如下：

```text
执行所有 Try
      │
      ▼
所有 Try 都成功？
      │
      ├── 否 ─────────► Cancel
      │
      └── 是
          │
          ▼
        Confirm
```

TCC 还需要处理三个问题：

- **幂等**：Confirm 和 Cancel 重复调用时，只能生效一次；
    
- **空回滚**：Try 尚未执行时，Cancel 不能错误释放资源；
    
- **事务悬挂**：Cancel 已执行后，延迟到达的 Try 不能再次冻结资源。
    

TCC 适合资金冻结、库存预占、优惠券锁定等核心业务，但每个参与者都需要实现 Try、Confirm 和 Cancel，业务侵入较大。

---

# 五、Saga 模式

Saga 适合跨多个服务的长业务流程。

它将一个全局事务拆分为多个独立提交的本地事务：

```text
T1：创建订单
T2：扣减库存
T3：完成支付
T4：增加积分
```

每个本地事务都需要对应一个补偿操作：

```text
T1 创建订单 ──► C1 取消订单
T2 扣减库存 ──► C2 恢复库存
T3 完成支付 ──► C3 发起退款
T4 增加积分 ──► C4 扣回积分
```

如果支付失败：

```text
创建订单成功
      │
      ▼
扣减库存成功
      │
      ▼
支付失败
      │
      ▼
恢复库存
      │
      ▼
取消订单
```

Saga 和 TCC 的主要区别是：

```text
TCC：
先预留资源，再 Confirm 或 Cancel。

Saga：
每一步直接提交，失败后执行反向补偿。
```

## 1. 编排式 Saga

编排式 Saga 由统一协调器控制整个流程。

```text
Saga 协调器
      │
      ├──► 订单服务
      ├──► 库存服务
      ├──► 支付服务
      └──► 积分服务
```

协调器负责：

- 决定下一步调用哪个服务；
    
- 记录当前执行状态；
    
- 判断是否需要补偿；
    
- 按顺序调用补偿接口。
    

例如库存扣减失败时，协调器直接调用订单服务取消订单。

编排式 Saga 的流程集中、状态清晰，适合步骤较多或分支复杂的业务，但协调器需要维护完整的业务流程。

## 2. 编舞式 Saga

编舞式 Saga 不设置统一协调器。

每个服务通过监听事件执行自己的本地事务，完成后再发布新的事件，由下一个服务继续处理。

正常流程如下：

```text
订单服务创建订单
      │
      ▼
发布“订单已创建”事件
      │
      ▼
库存服务扣减库存
      │
      ▼
发布“库存已扣减”事件
      │
      ▼
支付服务完成支付
      │
      ▼
发布“支付已完成”事件
      │
      ▼
订单服务更新订单状态
```

每个服务只需要知道：

- 自己监听什么事件；
    
- 收到事件后执行什么操作；
    
- 执行完成后发布什么事件。
    

例如：

```text
库存服务：
监听“订单已创建”事件，扣减库存。

支付服务：
监听“库存已扣减”事件，完成支付。

订单服务：
监听“支付已完成”事件，更新订单状态。
```

如果支付失败，支付服务发布失败事件，触发前面已经完成步骤的补偿操作：

```text
支付服务支付失败
      │
      ▼
发布“支付失败”事件
      │
      ▼
库存服务恢复库存
      │
      ▼
发布“库存已恢复”事件
      │
      ▼
订单服务取消订单
```

这里的恢复库存和取消订单，都是新的本地事务，而不是数据库回滚。

```text
原事务：扣减库存
补偿事务：恢复库存

原事务：创建订单
补偿事务：取消订单
```

编舞式 Saga 的核心是：

> 服务通过业务事件推动下一步操作，并通过失败事件或补偿事件恢复已经完成的步骤。

它和普通的消息通知不同，因为事件不仅用于传递结果，还共同组成了完整的事务流程和补偿流程。

编舞式 Saga 的服务耦合较低，适合参与者较少、流程较简单的业务。

当服务数量较多时，事件依赖会逐渐复杂，完整流程、补偿顺序和故障位置也会更难追踪。

无论采用编排式还是编舞式，Saga 都通过本地事务和补偿操作实现最终一致性。

# 六、本地消息表

本地消息表也称为 Outbox Pattern。

它将业务数据和待发送消息写入同一个本地事务：

```java
@Transactional
public void createOrder() {
    orderMapper.insertOrder();
    messageMapper.insertMessage();
}
```

本地事务可以保证：

```text
订单数据和消息记录同时提交
或者
订单数据和消息记录同时回滚
```

后台任务负责扫描并发送未处理消息：

```text
提交本地事务
      │
      ▼
扫描未发送消息
      │
      ▼
发送到 MQ
      │
      ▼
发送成功？
      │
      ├── 否 ─────────► 稍后重试
      │
      └── 是
          │
          ▼
      更新消息状态
```

消息发送成功后，如果应用在更新消息状态前宕机，后台任务可能再次发送同一条消息。因此，消费者必须实现幂等。

本地消息表不依赖 MQ 的事务能力，但需要维护消息表、扫描任务和历史数据。

---

# 七、事务消息

事务消息由消息中间件提供，例如 RocketMQ 事务消息。

它用于保证生产者本地事务与消息发送之间的一致性。

```text
发送半消息
      │
      ▼
半消息发送成功？
      │
      ├── 否 ─────────► 结束
      │
      └── 是
          │
          ▼
      执行本地事务
          │
          ▼
      本地事务成功？
          │
          ├── 否 ─────► Rollback
          │
          └── 是
              │
              ▼
            Commit
```

半消息已经存储在 Broker 中，但 Commit 前消费者无法读取。

如果生产者在本地事务执行完成后宕机，Broker 会回查事务状态：

```text
Broker 发起事务回查
      │
      ▼
本地事务状态明确？
      │
      ├── 否 ─────────► 返回 Unknown，稍后继续回查
      │
      └── 是
          │
          ▼
      本地事务是否成功？
          │
          ├── 否 ─────► Rollback
          │
          └── 是
              │
              ▼
            Commit
```

事务消息只保证生产者本地事务与消息发送的一致性。消费者仍然需要实现幂等、失败重试和异常补偿。

---

# 八、普通消息队列

普通 MQ 通过事件驱动，让不同服务分别完成自己的本地事务。

```text
订单服务创建订单
      │
      ▼
发送扣库存消息
      │
      ▼
库存服务扣减库存
```

MQ 通常提供消息持久化、失败重试、死信队列和延迟消息等能力。

但普通 MQ 无法单独保证数据库事务与消息发送同时成功：

```text
订单写入成功
      │
      ▼
发送消息前应用宕机
      │
      ▼
库存服务无法收到消息
```

因此，普通 MQ 通常需要结合：

- 本地消息表；
    
- 事务消息；
    
- Binlog / CDC；
    
- 定时补偿；
    
- 数据对账。
    

普通 MQ 是异步通信基础设施，只有结合可靠投递、消费幂等和失败补偿后，才能用于实现最终一致性。

---

# 九、方案对比

|方案|核心机制|失败处理|业务侵入|适用场景|
|---|---|---|--:|---|
|XA / 2PC|统一准备和提交|数据库回滚|较低|短事务、跨数据库原子提交|
|3PC|预检查、预提交、正式提交|协调回滚|较低|实际使用较少|
|AT|Undo Log + 全局锁|框架自动补偿|较低|普通关系型数据库业务|
|TCC|业务资源预留|Cancel 释放资源|很高|资金、库存等核心业务|
|Saga|本地事务链|反向业务补偿|较高|跨服务长业务流程|
|本地消息表|业务与消息同库提交|消息重试|中等|可靠事件投递|
|事务消息|半消息 + 事务回查|提交或回滚消息|中等|本地事务与 MQ 一致|
|普通 MQ|异步事件驱动|重试、死信、补偿|较低|通知、积分、索引更新|

---

# 十、方案选择

```text
短事务，数据库支持 XA：
选择 XA / 2PC。

关系型数据库业务，希望降低代码侵入：
选择 AT。

业务可以冻结资金或预占库存：
选择 TCC。

跨多个服务的长业务流程：
选择 Saga。

需要保证本地事务后消息一定发送：
选择本地消息表或事务消息。

通知、积分、缓存、搜索索引等异步业务：
选择 MQ + 重试、幂等和补偿。
```

无论采用哪种方案，都需要考虑：

- 幂等；
    
- 失败重试；
    
- 事务状态记录；
    
- 超时处理；
    
- 补偿失败处理；
    
- 定时对账。
    

---

# 十一、总结

```text
XA / 2PC：
参与者先准备，再由协调器统一提交或回滚。

3PC：
在 2PC 的基础上增加预提交和超时机制。

AT：
本地事务先提交，框架通过 Undo Log 自动补偿。

TCC：
先预留业务资源，再执行 Confirm 或 Cancel。

Saga：
多个本地事务依次提交，失败后执行反向补偿。

本地消息表：
业务数据和消息记录在同一个本地事务中提交。

事务消息：
通过半消息、本地事务和事务回查保证消息可靠发送。

普通 MQ：
结合可靠投递、重试、幂等和补偿实现最终一致性。
```

一句话概括：

> XA / 2PC 通过提交前统一协调保证原子提交；AT、TCC 和 Saga 通过事务状态与补偿恢复一致；消息方案通过可靠投递、重试、幂等和对账达到最终一致。
