1.2 平台差异说明

任务书与实验指南的首选平台是 Ubuntu/Debian，次选是 Windows 下的 WSL2，并明确指出"Git Bash 本身不能代替完整编译环境"。本机无法启动 WSL，因此本次实验采用第三条路径：直接使用 MinGW-w64 的原生 GNU 工具链。这一选择带来了三个必须在报告中交代的差异，它们也恰好成为观察编译系统的一个额外视角：

  1. 目标文件格式不同。file hello.o 得到的是 x86-64 COFF object file，而不是 Linux 上的 ELF 64-bit LSB relocatable；节（section）的名称、objdump -r 打印的重定位类型（IMAGE_REL_AMD64_REL32）也与 ELF 的 R_X86_64_PLT32 不同。但"符号表 + 重定位表"这套结构在两种格式中是对应的。
  2. 可执行文件后缀与格式不同。本机生成的产物带 .exe 后缀，file 报告 PE32+ executable for MS Windows 5.02 (console), x86-64。
  3. 启动代码对入口的期望不同。Linux 上缺少 main 时链接器报 undefined reference to 'main'；本机 MinGW 的 C 运行时启动对象 crtexewin.o 同时接受 main 与 WinMain，因此报错变成了 undefined reference to 'WinMain'（见 3.5 节）。这是同一条规则在不同 C 运行时实现下的表面差异。

为什么这个差异值得记录

指南反复强调"输出细节以本机为准"。把这三条差异写清楚，本身就说明我理解了四阶段是工具链的外部流程，而文件格式、符号命名（如 macOS 的 _main）只是该流程在不同平台上的具体实现，不影响阶段划分。

第 2 章　走近 GCC：从源代码到可执行文件

2.1 GCC 是驱动程序，不是"一个编译器"

在做实验之前，我对 gcc 的理解停留在"把 .c 变成 .exe 的东西"。任务 1.1 的第一个认知转变是：gcc 本身几乎不做任何编译工作，它是一个驱动程序（driver）——负责按命令行参数决定在哪个阶段停下，然后依次启动 cc1（真正的 C 编译器）、as（汇编器）、collect2/ld（链接器），并负责把临时文件名拼接好传下去。

因此 -E/-S/-c 三个选项的本质是"在哪个阶段之后停下"，而 -o 只决定输出文件叫什么名字，不决定停在哪儿。这一点在 3.6 节用 -### 得到了直接验证。

2.2 第一次编译

源文件 hello.c 只用了三个语言要素：宏定义、一个普通函数、一次格式化输出。GREETING 是宏，它在预处理阶段就会被替换成字符串字面量，这一点在 3.2 节可以直接看到证据。

#include <stdio.h>
#define GREETING "Hello, Compiler!"
int add(int a, int b) { return a + b; }
int main(void) {
    int x = 2, y = 3;
    printf("%s %d + %d = %d\n", GREETING, x, y, add(x, y));
    return 0;
}
终端实录 2-1　最简编译流程与产物类型
$ gcc hello.c -o hello.exe
$ ./hello.exe
Hello, Compiler! 2 + 3 = 5
$ file hello.exe
hello.exe: PE32+ executable for MS Windows 5.02 (console), x86-64, 16 sections

输出与指南预期（Hello, Compiler! 2 + 3 = 5）完全一致。这里值得多看一眼的是 file 的返回值：它没有说"这是个 C 程序"，也没有说"这是 GCC 编译的"，它只报告了容器格式（PE32+）、目标平台（MS Windows 控制台）、指令集（x86-64）和节数量（16）。这说明从 .c 到可执行文件，语言的痕迹已经完全消失，剩下的只是操作系统能装载的二进制结构。如果换到 Linux，这一行会变成 ELF 64-bit LSB pie executable, x86-64, dynamically linked，信息量相同但格式不同。

2.3 读一条错误信息

指南要求"故意制造语法错误并读懂 GCC 的错误信息"。我用的 bug.c 少了一个右括号和一个分号：

#include <stdio.h>
int main(void) {
    printf("hello" // 缺少右括号
    return 0;
}
终端实录 2-2　语法错误的完整诊断
$ gcc bug.c -o bug.exe
bug.c: In function 'main':
bug.c:3:19: error: expected ')' before 'return'
    3 |     printf("hello" // 缺少右括号
      |           ~       ^
      |                   )
    4 |     return 0;
      |     ~~~~~~
bug.c:4:14: error: expected ';' before '}' token
    4 |     return 0;
      |              ^
      |              ;
    5 | }
      | ~

这条诊断可以按四层来读，每一层都有明确含义：

  1. 定位：bug.c:3:19 是"文件:行:列"，第 3 行第 19 列正是字符串字面量 "hello" 结束之后的位置。
  2. 性质：error（而非 warning），意味着后续阶段无法继续，不会生成目标文件。
  3. 期望：expected ')' before 'return'——编译器在此处期待的是一组函数的收尾（右括号与分号），却读到了 return 这个关键字。
  4. 建议：下方用 ^ 指位置、用 ~ 划出问题片段，并在下一行直接给出了补上 ) 的修复示意。这是 GCC 的"修复提示"（fix-it hint），不是装饰。

第二条 expected ';' before '}' token 是典型的级联错误：解析器在第一条错误后为了继续往下读，按"已经补上右括号"的假设继续解析，于是 return 0; 之后又缺了属于 printf 语句的那个分号。这带来一条很实用的经验：错误信息要自上而下读，先改第一条，重新编译，再看剩下几条；一次性照单全收地改，往往会把没问题的代码改坏。

修复版 bug_fixed.c 补上了 ) 与 ;，并额外加了 \n（原代码即使补全括号，输出也会和 shell 提示符挤在同一行）。修复后编译运行输出 hello，退出码为 0。

2.4 多文件、外部符号与链接错误

把 add 拆到独立编译单元后，main.c 只能通过 extern 声明"这个函数在别处定义，签名如下"来调用它。extern 声明是对编译器的承诺，而不是对链接器的保证——这正是链接错误产生的土壤。

/* add.c */                        /* main.c */
int add(int a, int b) {            #include <stdio.h>
    return a + b;                  extern int add(int, int);
}                                  int main(void) {
                                       printf("3 + 5 = %d\n", add(3, 5));
                                       return 0;
                                   }
终端实录 2-3　缺少定义时的链接错误，以及补齐后的成功链接
$ gcc main.c -o broken.exe
ld.exe: .../ld.exe: C:\Users\...\Temp\ccjDSCxr.o:main.c:(.text+0x18):
        undefined reference to `add'
collect2.exe: error: ld returned 1 exit status
$ gcc main.c add.c -o two_files.exe
$ ./two_files.exe
3 + 5 = 8

这条报错的三个细节分别对应链接器的工作内容：

  • ccjDSCxr.o：gcc 在临时目录生成的中间目标文件。注意这里是 .o 而不是 .c——说明编译已经成功，失败发生在链接阶段。
  • main.c:(.text+0x18)：链接器把出错位置定位到 .text 段偏移 0x18 处，也就是 call add 那条指令。它知道"有个调用指令要填地址，但地址填不上"。
  • undefined reference：符号解析失败。链接器在所有输入目标文件和库的符号表里都找不到名为 add 的已定义符号，只有一个"未定义引用"。

而 gcc main.c -o broken.exe 之所以编译阶段不报错，是因为 C 采用分别编译：编译 main.c 时，编译器只检查 extern int add(int, int); 这个声明与调用处的实参是否匹配，它有权利相信"定义在别的编译单元里"。验证是否真的存在这个定义，是链接器的职责。这也是为什么多文件项目的错误定位会"跳":语法错在编译期暴露，符号错要到链接期才暴露。

  2. 1526 行里绝大多数不是自己写的代码。原始文件只有 8 行，预处理后膨胀到 1526 行，差额来自 <stdio.h> 及其递归包含的一串内部头文件（corecrt.h、corecrt_stdio_config.h 等）。这解释了"为什么编译同样一份代码，换一套 C 库行数就变"。
  3. 以 # 开头的行多半不是未展开的宏。指南特别提醒过这一点：这里的 98 个 # 行是行标记（line marker），格式为 # 行号 "文件名" 标志，供编译器在报错时反查"这段代码原本来自哪个文件的第几行"。也正因为有行标记，预处理后的错误还能定位回 hello.c。

第 4 章　编译选项实验：性能与诊断的取舍

本章包含四个必做实验。与前两章"看清工具做了什么"不同，本章的目标是建立选型判断：什么样的场景该用哪一档优化、什么时候必须加 -g、警告应该开到什么程度。

4.1 实验 1：优化等级对比

被测程序是一个求和循环，数学上 sum = Σ(2i+1) = N²，当 N = 10 000 000 时结果应为 100000000000000。四个版本都用 clock() 只包住循环区间，以排除 printf 的影响。

选项 文件大小 / B 代码段 / B 汇编行数 循环 CPU 时间 / 秒（9 次采样） 中位数
-O054 51711 420890.013 0.009 0.008 0.010 0.009 0.017 0.011 0.013 0.0150.011

注：四个版本 sum 输出均为 100000000000000，与 N² 一致；"代码段"取自 size 命令的 text 列。

发现一：-O1 把算术优化掉了，却把循环留了下来

这是我本次实验中最意外的观察。-O1 的汇编里已经出现 movabsq $100000000000000, %rdx——说明 sum 被编译期常量折叠了，循环体内那 sum += i*2+1 的算术完全消失；但循环本身还在，被降级成了一个纯粹的空转计数器：

# -O1 生成的 main 片段
        call    clock
        movl    %eax, %esi
        movl    $10000000, %eax        # 只剩计数
        .p2align 3
.L2:
        subq    $1, %rax
        jne     .L2
        call    clock

而 -O2/-O3 连这个空循环也删了，两次 clock() 调用紧挨在一起：

# -O2 生成的 main 片段
        call    clock
        movl    %eax, %esi
        call    clock
        ...
        movabsq $100000000000000, %rdx

这就解释了一个乍看矛盾的现象：-O1 明明已经不做算术了，计时却还有 3 毫秒；-O2 才是真正的 0。原因很直接——那 1000 万次 subq/jne 是真实执行的指令。-O1 处于一个"半优化"的中间态：语义已经等价化简，但冗余结构尚未清理。从工程角度看，这是最需要警惕的一档：既没有 -O0 的可调试性，也没有 -O2 的性能。

发现二：文件大小不能用来看优化效果

表 4-1 里 -O0 与 -O1 的可执行文件同为 54 517 B，-O2/-O3 反而各多了 36 B。如果只看文件大小，会得出"越优化越大"的错误结论。原因是 PE 格式有节对齐与冗余填充，几十字节的代码差异被对齐开销掩盖了。改用 size 读代码段才看得出真实趋势：11 420 → 11 324 → 11 324 → 11 324，优化收益集中在 -O0 到 -O1 这一步，-O1 之后代码段不再变化——因为剩下的差异都已变成"删掉整段代码"，而删除发生在节内，被对齐吸收了。结论：比较优化效果应当看代码段大小与关键路径指令数，而不是 ls -l。

发现三：优化档位是一组开关的集合

用 gcc -Q --help=optimizers 统计每个档位实际打开的优化器数量，得到 -O0 51 项、-O1 93 项、-O2 142 项、-O3 155 项。这组数字比"-O3 最强"这种印象更有解释力：-O1 → -O2 增加了 49 个开关（含大量向量化前置分析），-O2 → -O3 只增加 13 个（主要是更激进的向量化与内联）。这也解释了为什么 O2 与 O3 在本例中产物完全相同——这段代码没有可向量化的对象，-O3 多出来的开关找不到施展空间。

发现四：time 命令测的不是这段循环

终端实录 4-1　终端 time 与程序内 clock() 的对比
$ time ./loop_O0.exe > /dev/null
real    0m0.682s
user    0m0.031s
sys     0m0.250s
$ time ./loop_O3.exe > /dev/null
real    0m0.690s
user    0m0.125s
sys     0m0.218s

两个版本的 real 几乎一样（0.68 s 与 0.69 s），但这个时间几乎全部来自进程创建与 C 运行时初始化，而不是循环本身——循环在 -O0 下也只要 11 ms。指南之所以要求"两种计时分开记录"，原因就在这里：clock() 测的是进程内的 CPU 时间（且不含后续 printf），time 测的是整条命令从创建到回收的墙钟时间。用后者去比较 10 ms 级别的差异，只会得到噪声。

关于 0.000000 的处理

-O2/-O3 的九次采样全部为 0.000000。按指南要求，这类结果不能记成"0 秒、性能无限好"，而应标注为无法可靠区分——因为此时两次 clock() 调用之间已经没有任何用户代码，测量值落到了计时分辨率以下。这里另有一条纪律：不能为了让计时"有数"而给循环加 volatile，那会改变本实验要观察的优化条件，让对比失去意义。

4.4 实验 4：预处理宏

终端实录 4-5　-DDEBUG 控制条件编译
$ gcc -O0 test.c -o test_off.exe && ./test_off.exe
answer = 42
$ gcc -O0 -DDEBUG test.c -o test_on.exe && ./test_on.exe
[DEBUG] x = 42
answer = 42
$ strings test_off.exe | grep -c "\[DEBUG\]"
0
$ strings test_on.exe | grep -c "\[DEBUG\]"
1

-DDEBUG 等价于在源文件最前面写 #define DEBUG 1，于是 #ifdef DEBUG 包住的那条 printf 被保留，其余情况被整段删除。strings 的结果给了更硬的证据：不定义 DEBUG 时，那行调试字符串根本不存在于可执行文件中——它不是"运行时被跳过"，而是"编译时就没有生成"。这与 if (debug) {...} 这类运行期开关有本质区别：后者会留下分支和字符串，前者零开销。

一个容易混淆的点

-DDEBUG 与 -g 完全不等价，二者作用在不同阶段：-DDEBUG 是预处理阶段的文本开关，决定哪些代码进入编译；-g 是汇编/链接阶段附加的元数据，不改变一行机器码，只让调试器能看懂它。可以同时使用，也可以只用其一。本实验中 test_on.exe 并没有加 -g，它输出调试日志靠的是源码里的宏，与调试信息无关。

5.1 三段式结构与工作流

5.2 实验 1：最简整数识别器

demo.l 只有三条规则：识别连续数字、跳过空白、丢弃其他字符。它完整展示了"生成—编译—运行"的全过程，也让 yytext 和动作代码的写法落到实处。

输出与预期一致。hello 被最后一条 . 规则逐字符丢弃，所以只留下两个整数。这条 . 规则是"兜底"——它保证任何字符都有规则可匹配，否则 Flex 的默认动作是把不匹配的字符原样回显到标准输出，行为会与预期不符。这也是后面两个练习要保留 UNHANDLED 提示的原因。

为什么 DEC 不写成 [0-9]+

如果 DEC 写成 [0-9]+，那么输入 075 时，DEC 与 OCT 都能匹配 3 个字符，形成等长并列，Flex 只能退回"选靠前的规则"，于是类别取决于书写顺序——这不是我们想要的语义。写成 0|[1-9][0-9]* 后，DEC 在正规式层面就无法匹配"以 0 开头的多位数字"，075 只有一个规则能匹配到 3 个字符，歧义在设计阶段就被消除。这是本实验里最值得记住的一条经验：能用正规式表达清楚的地方，不要交给规则顺序去兜底。

  1. 局部匹配不等于整体合法。08 被切成 0 和 8 两个 DEC，程序"成功识别了"，但 08 这个整体既不是合法八进制也不是合法十进制。12abc 同理。指南要求"不能把若干局部匹配当作整个数字合法"，指的正是这种情况。词法分析器只负责切分，合法性判断要靠后继阶段。
  2. .5 与 1. 的不对称，是规则设计的结果，不是 bug。因为我按指南把"简单浮点数"定义为小数点两侧都有数字，所以这两个输入各自只完成一半匹配。如果允许 .5 或 1. 成立，正规式要改成 [0-9]*\.[0-9]+ 之类，会与"小数点两侧均有数字"的要求冲突。
  3. 负号必须由独立的运算符规则处理。-12 中被切出的 - 是 UNHANDLED，因为 numbers.l 没有定义运算符。若真的加上负号识别，正确做法是让 - 成为独立的运算符记号，而不是把它并进数字规则——否则 a-12 这类表达式会被切错。

5.5 最长匹配与等长规则优先级

Flex 的选择规则可以精确地写成两句：

  1. 最长匹配优先：在所有能匹配当前位置的规则中，选匹配文本最长的那一条。这与规则书写顺序无关。
  2. 等长时取靠前者：若多条规则匹配到同样长的文本，选在 .l 文件中出现得更早的那一条。

等长优先int → KW: int（两条规则都是 3 个字符，关键字在写前面）若反过来把 ID 写在前面，关键字会在编译期全部退化为标识符（即终端实录 5-4 的结果）

指南要求"给出一个自测反例"，我用的是 intx：它同时是"关键字前缀 + 后缀"的形式，若实现采用"先试关键字、成功即返回"的策略，就会被切成 KW: int 与 ID: x；实际输出是 ID: intx，说明最长匹配确实在所有规则之间统一比较。另一个方向的反例是 int 本身：它无法用长度区分，只能靠顺序——这就是为什么所有 C 风格词法分析器都把关键字规则写在标识符规则之前。

5.6 从正规式到自动机

本实验只要求理解"正规式用于描述词法规则，Flex 借助自动机完成识别"这一层关系，具体构造算法留给项目 2。不过 lex.yy.c 里已经能看到不少线索：生成文件中有 yy_accept[] 这样一张状态接受表，以及 yy_current_state 的状态转移驱动循环。

终端实录 5-5　生成文件中与自动机有关的结构
$ grep -n "yy_accept\[" lex.yy.c | head -2
366:static const flex_int16_t yy_accept[20] =
696:            if ( yy_accept[yy_current_state] )

这段代码透露的实现方式可以概括为：每条正规式先被转换成 NFA，多条规则合并成一个 NFA，再确定化为 DFA，最后把 DFA 压缩成两张表——转移表与接受表。yy_accept[state] 给出"到达该状态时接受哪条规则"，第 696 行那句判断正是"如果当前状态是接受态，就记下它（以便继续往后试更长的匹配）"。这恰好解释了最长匹配是怎么实现的：扫描时不断前进，把最近一次遇到的接受态记下来；走到不能再走时，回退到那个接受态并按对应规则执行动作。所谓"最长"，在实现上就是"最后一次能接受的位置"。

这也解释了为什么 numbers.l 里 DEC 写成 0|[1-9][0-9]* 比写成 [0-9]+ 更稳妥：前者让自动机在读完 0 之后对"下一位是数字"这件事不再有接受路径，后者会造出一条与 OCT 并行的长路径，两个接受态指向不同规则，最终只能靠规则编号（即书写顺序）打破平局。项目 2 会亲手做 Thompson 构造与子集构造，那时这张表将被完整地推导一遍。

第 6 章　思政融合：国产编译器调研

6.1 调研对象

本次调研选择华为毕昇编译器（BiSheng Compiler）。按 openEuler 软件包仓库的官方描述，它是"华为编译器实验室针对鲲鹏等通用处理器架构场景，打造的一款高性能、高可信及易扩展的编译器工具链"，通过增强和引入多种编译优化技术，为 ARM 服务器平台提供从源码到二进制的完整编译能力[1]。选择它的理由很直接：它是国内少数已经进入主流 Linux 发行版软件源、可以被普通用户 yum install 下来直接使用的自研编译器，而不是停留在发布会上的概念产品。

6.2 关键发现

（1）支持语言：C / C++ / Fortran 三线并行

毕昇编译器不自己发明语言，而是复用 LLVM 生态的前端：C 与 C++ 交由 Clang 完成词法、语法、语义分析与 LLVM IR 生成，同时 Clang 兼任驱动程序；Fortran 交由 Flang 完成，官方文档特别指出 Flang 由 flang1 与 flang2 两个组件构成，同样是"把源码转成 LLVM IR"的驱动[1]。这一点与我在第 2 章看到的 GCC 结构形成了有趣的对照：GCC 的 C 前端 cc1 是一个高度集成的单体程序，而 LLVM 系的前端是按库拆分的。

（2）目标架构：以 AArch64 / 鲲鹏为主战场

官方安装文档把"架构"一栏直接写死为 AArch64，软件源路径也是 repo.oepkgs.net/bisheng/aarch64/[1]。这说明毕昇的定位不是"通用跨平台编译器"，而是面向 ARM 服务器、特别是鲲鹏处理器的深度定制。鲲鹏社区的文章也印证了这条路线：面向 x86 迁移到鲲鹏的场景，华为提供毕昇编译器、毕昇 JDK、GCC for openEuler 三件套，分别对应高性能计算、Java 业务和通用场景[2]。

（3）工具链组成：驱动 + 前端 + 链接器，全部可替换

编译 C/C++ 用 clang / clang++，编译 Fortran 用 flang；链接默认调用系统 ld，但可以通过 -fuse-ld=lld 换成 LLVM 自己的 lld[1]。这个细节值得注意——编译器和链接器是解耦的，这与我在 3.6 节用 -### 看到的 collect2 → ld 是同一套分工思路。安装方式上，openEuler 已把毕昇收进官方源，yum install bisheng-compiler 即可；非 openEuler 系统则通过新增 bisheng-compiler.repo 的方式接入[1]。

（4）一项有来源支持的技术特征：中后端深度优化 + Auto-tuner

官方文档的表述是："除 LLVM 通用功能和优化外，毕昇编译器的工具链对中端及后端的关键技术点进行了深度优化，并集成 Auto-tuner 特性支持编译器自动调优"[1]。这里有两个可核查的点：其一，优化发生在中端（IR 层）与后端（目标代码层），而不是只在前端做语法层面的把戏——这与第 4 章观察到的 -O1 常量折叠、-O2 死代码消除属于同一层级的工作；其二，Auto-tuner 是一种"自动搜索编译参数"的机制，它需要反复编译、运行基准程序并测量，本质上把"人工试 -O2 还是 -O3、要不要开某个 -march"这件事交给机器迭代。这正是第 4 章那张"按场景选选项"表格的自动化版本。

性能方面，鲲鹏社区的对比口径是：在 SPEC CPU 2017 测试中，毕昇编译器相比开源 GCC 9.3 性能提升约 25%，在 WRF、CUACE 等专业应用中提升约 10%[2]。需要说明，这是厂商公布的测法，测试平台、基线与编译选项都以对方口径为准，不宜直接外推到自己手上的程序。

6.3 我的思考：从"用工具"到"想工具"

做完项目 1 再回头看毕昇，最强烈的感受是"四阶段"这套骨架是跨编译器的通用语言。clang -E、clang -S、clang -c 与 GCC 的同名选项语义一致，因为二者都是"驱动程序 + 前端 + 优化器 + 后端 + 汇编器 + 链接器"的结构，只是前端实现方式不同。这意味着我在第 3 章学到的观察方法——用 -E 看宏展开、用 -S 看指令、用 nm 看符号、用 objdump -r 看重定位——换成任何一款类 LLVM 的编译器都仍然有效。工具会换，方法论不会。

更值得记住的是差异背后的原因。GCC 的 cc1 是单体可执行文件，Clang 是库化的：libclang 可以被 IDE、静态分析器、代码补全工具直接调用，所以你会看到 VS Code、CLion 都能读懂 C++ 而不仅仅是"调用编译器"。这解释了为什么 LLVM 生态在工具化、可复用性上扩张得这么快，也解释了国产编译器为什么普遍选择"基于 LLVM 深度定制"而不是"从零写一个 GCC"——站在成熟的开源基础设施上做增量创新，是更现实的技术路线。

局限同样清楚。第一，架构绑定：官方文档把架构限定为 AArch64，意味着在 x86 开发机上无法直接使用，迁移成本落在"有没有 ARM 机器"这一步。第二，生态依赖：它需要系统已有的 GCC（≥4.8.5）、glibc（≥2.17）、libstdc++（≥6）、libatomic（≥1.2）作为地基[1]，并不是完全自包含的工具链——这既是优势（与系统 ABI 天然兼容），也意味着它无法脱离 Linux 发行版的包管理体系独立存在。第三，调优的时间成本：Auto-tuner 靠反复编译测量来收敛，对"一天构建几十次"的开发流程并不友好，更适合发布前的最终构建。

关于"一次可复现体验"，我设计了如下步骤，作为后续在鲲鹏环境上的验证方案（本机为 x86_64 Windows，无法直接执行）：在 openEuler AArch64 机器上执行 yum install bisheng-compiler，用 clang -v 确认版本；然后对项目 1 的 hello.c 分别执行 clang -E、clang -S、clang -c，把三份产物与本次 GCC 的 hello.i、hello.s、hello.o 并排比较：预期会在 .i 的行标记格式、.s 的伪指令（GCC 用 .seh_*，Clang 风格不同）、.o 的节名与符号修饰上看到差异，但四个阶段的划分、nm 中 T/U 的含义、objdump -r 的重定位项应当保持一致。如果这三条一致，就说明"四阶段"确实是工具链层面的客观结构，而不是某一家编译器的实现细节。

还有一点体会来自"编译器为什么是基础软件"。第 4 章里，同一段循环在 -O0 下要跑 11 ms，在 -O2 下被彻底消除——编译器不动一行源码，就能决定程序的性能上限。把这个尺度放大到一个数据中心、一座超算集群，编译器的差距就是电费、机时和能耗的差距。这大概就是"卡脖子"三个字在编译领域的具象含义：它不在应用层，而在所有人都站在上面的那一层。

第 7 章　综合反思

7.1 最有趣的环节：-O1 留下的那个空循环

如果只能留一个发现，我会留 4.1 节那个：-O1 已经把 sum 折叠成常量 100000000000000，却仍然保留了 subq $1, %rax / jne .L2 这样一对空的计数指令，导致"算术都不做了，计时还有 3 毫秒"。它推翻了我原先"优化等级是一个单调的滑杆"的直觉——真实情况是一组彼此独立的变换，各自有不同的触发条件。常量折叠在 -O1 就会发生，而死循环消除要等到 -O2。这也让我第一次具体地理解了"半优化状态"为什么不安全：既丢了可调试性，又没拿到性能。

7.2 最大的收获：把"编译"从一个词拆成了一条流水线

做实验之前，"编译"对我是一个不可分割的动作；做完之后，它变成了五样东西、四个阶段、两个关键机制（符号解析与重定位）。最实用的三个收获是：

  1. 出错时先判断"错在哪个阶段"。语法错带行列号、发生在编译期；undefined reference 发生在链接期，报的是目标文件名而不是源文件名。这个区分能省掉大量无谓的排查——我原来会去检查 #include，现在会先看它是 .c 还是 .o。
  2. -### 是理解工具链最快的入口。与其去背"四阶段"，不如看一眼它实际调了哪几个程序、临时文件怎么命名。这一条对以后接触任何新编译器都适用。
  3. 能交给正规式解决的歧义，不要留给规则顺序。5.3 节把 DEC 写成 0|[1-9][0-9]* 而不是 [0-9]+，效果是把"075 算 DEC 还是 OCT"这个顺序依赖问题在源头消除了。这条经验不只用于 Flex。

7.3 还存在的疑问

  1. 为什么 -O2 的可执行文件反而比 -O0 大 36 字节？代码段明明更小（11 324 < 11 420）。我推测是 PE 的节对齐（FileAlignment / SectionAlignment）与重定位、导入表布局变化造成的，但没有逐节比对 objdump -h 的文件偏移，还不能下结论。
  2. clock() 在本机的分辨率到底是多少？-O0 的九次采样从 0.008 s 波动到 0.017 s，跨度接近一倍。CLOCKS_PER_SEC 在 Windows 上定义为 1000，但底层时钟源的实际粒度、以及它是否受 CPU 频率调节影响，我没有验证。-O2 的九次全 0 说明粒度至少不劣于 1 ms，但"1 ms 以下的东西测不出来"这件事本身需要确认。
  3. Flex 生成的表是怎么压缩的？生成文件里 yy_accept[20] 只有 20 项，而规则有 5 条、状态显然不止 20 个——说明状态编号经过了重新映射，还可能用了等价类合并（把输入字符分成若干等价类以减少表宽）。这部分属于 DFA 最小化与表压缩，项目 2 应该会展开。
  4. 如果把 hello.c 换成 Clang 编译，四阶段的产物差异会有多大？这是第 6 章那份验证方案要回答的问题，目前只有推断，没有实测。

7.4 关于实验方法的一点体会

这次实验里我最刻意坚持的一件事，是凡是"预期"和"实测"不一致的地方，都写清楚不一致本身。比如指南说 file hello 应显示 ELF，我的机器显示 PE32+；指南说缺 main 会报 undefined reference to 'main'，我的机器报 WinMain。把这些差异当成"实验结果的一部分"记录，比强行对齐预期更有价值——它们恰好说明四阶段是抽象结构，而格式与命名是实现细节。同样地，五类警告我没有照抄指南的行号，而是记录本机实际报出的 2:28、4:9 等位置；优化对比表填的是九次采样的中位数，而不是单次结果。这些做法让报告里的每个数字都可以被复现。
