第 2 章　走近 GCC：从源代码到可执行文件

2.1 GCC 是驱动程序

gcc 本身几乎不做编译工作，它是驱动程序：按参数决定停在哪个阶段，再依次调起 cc1（C 编译器）、as（汇编器）、collect2/ld（链接器）。因此 -E/-S/-c 的含义是"停在哪个阶段之后"，而 -o 只决定输出文件名，与停止位置无关。

2.3 读一条错误信息

bug.c 在 printf("hello" 后缺少右括号与分号：

终端实录 2-2　语法错误诊断
$ gcc bug.c -o bug.exe
bug.c: In function 'main':
bug.c:3:19: error: expected ')' before 'return'
    3 |     printf("hello" // 缺少右括号
      |           ~       ^
      |                   )
    4 |     return 0;
      |     ~~~~~~
bug.c:4:14: error: expected ';' before '}' token
    4 |     return 0;
      |              ^
      |              ;

诊断分四层：定位（3:19 即字符串字面量结束处）、性质（error 而非 warning，不会生成目标文件）、期望（此处期待函数调用的收尾却读到 return）、建议（用 ^ 指位并给出补上 ) 的修复示意）。第二条 expected ';' 是级联错误：解析器按"已补上右括号"的假设继续读，于是又发现 return 0; 缺分号。所以错误要自上而下逐条修，改一条重编译一次。bug_fixed.c 补上 ) 与 ;（另加 \n 防止输出与提示符同行）后编译运行正常。

3.2 预处理：宏消失，头文件铺开

终端实录 3-1　生成并检查 .i
$ gcc -E hello.c -o hello.i
$ wc -l hello.i
1526 hello.i
$ grep -c '^#' hello.i
98
$ grep -n "Hello, Compiler" hello.i
1524:    printf("%s %d + %d = %d\n", "Hello, Compiler!", x, y, add(x, y));

三个结论：宏已不存在——源文件里的 GREETING 在第 1524 行只剩 "Hello, Compiler!" 字面量，预处理是纯文本替换；1526 行里绝大部分是 <stdio.h> 递归包含的内部头文件，自己写的只有 8 行；以 # 开头的 98 行不是未展开的宏，而是行标记（# 行号 "文件名" 标志），供编译器报错时反查源码位置。用 -P 抑制行标记后行数降为 1165，差额 361 行即标记与空行。

3.3 编译与汇编：从 C 文本到目标文件

终端实录 3-2　编译成汇编
$ gcc -S hello.i -o hello.s
$ wc -l hello.s
57 hello.s
$ grep -n -E '^_?main:' hello.s
29:main:
终端实录 3-3　汇编成目标文件，观察符号与重定位
$ gcc -c hello.s -o hello.o
$ file hello.o
hello.o: x86-64 COFF object file, no line number info, not stripped,
         7 sections, symbol offset=0x2ac, 22 symbols, ...
$ nm hello.o
0000000000000000 T add
0000000000000014 T main
                 U printf
                 U __main
$ objdump -r hello.o
RELOCATION RECORDS FOR [.text]:
OFFSET           TYPE                   VALUE
000000000000001d IMAGE_REL_AMD64_REL32  __main
0000000000000047 IMAGE_REL_AMD64_REL32  .rdata
000000000000004e IMAGE_REL_AMD64_REL32  .rdata
0000000000000057 IMAGE_REL_AMD64_REL32  printf

.s 里 add: 在第 6 行、main: 在第 29 行，与源码顺序一致；本机汇编带大量 .seh_* 伪指令，是给链接器提供 Windows x64 结构化异常处理所需的栈展开信息，Linux 上没有。目标文件是信息量最大的一环：T 表示已定义符号（位于 .text 段），U 表示"本单元用到但没定义"，要留给链接阶段在 C 运行库里解决；.rdata 存字符串常量；4 条 REL32 重定位记录说明这些指令里的地址暂时填 0，等链接器确定最终地址后回填。__main 是 MinGW 特有的运行库初始化调用，Linux 的 GCC 不产生——这正是"可重定位目标文件必须留未定义符号"的原因：编译一个文件时，编译器不可能知道别的文件或运行库里有什么。

3.4 链接：符号解析与重定位

终端实录 3-4　单独链接 hello.o 即可运行；两个 .o 组合同样可行
$ gcc hello.o -o hello_from_o.exe && ./hello_from_o.exe
Hello, Compiler! 2 + 3 = 5
$ gcc main.o add.o -o two_files_o.exe && ./two_files_o.exe
3 + 5 = 8
$ gcc add.o -o no_main.exe
ld.exe: .../libmingw32.a(...crtexewin.o):crtexewin.c:(.text.startup+0xb4):
        undefined reference to `WinMain'
collect2.exe: error: ld returned 1 exit status

只给 .o 就能链接成功，说明链接器需要的是符号表与重定位表，不需要源码：printf、__main 由 C 运行库提供（ldd 显示依赖 ucrtbase 等），4 个待填地址在链接时回填。缺少入口的报错与指南的 Linux 版本（undefined reference to 'main'）文本不同、原因相同：链接器把 C 运行时启动对象也链了进来，它需要一个入口符号交出控制权，MinGW 实现里最后尝试的是 WinMain。

终端实录 3-5　-### 打印的流水线（节选）
$ gcc -### hello.c -o hello_trace 2> trace.txt
$ wc -l trace.txt

$ grep -o "cc1\.exe\|as\.exe\|collect2\.exe\|ld\.exe" trace.txt | sort | uniq -c

打印出的命令证实了三点：四阶段是被"接力"执行的——cc1 的输出直接写成临时 .s，as 拿它写成临时 .o，再交给 collect2（ld 的包装器，额外负责收集构造/析构信息），临时文件名每次随机生成；-### 确实什么都没生成，与 -v（真的编译并打印）不同；所谓"驱动程序"，就是把这几条命令按依赖顺序拼起来执行的那个角色。

第 4 章　编译选项实验：性能与诊断的取舍

4.1 实验 1：优化等级对比

被测程序是求和循环 sum = Σ(2i+1) = N²（N = 10 000 000，结果应为 100000000000000，四个版本输出均正确）。clock() 只包住循环区间，排除 printf 影响；每个版本采样 9 次取中位数。

选项 文件大小 / B 代码段 / B 汇编行数 循环 CPU 时间 / 秒（9 次采样） 中位数
-O054 51711 420890.013 0.009 0.008 0.010 0.009 0.017 0.011 0.013 0.0150.011
-O154 51711 324720.003 0.003 0.004 0.007 0.003 0.003 0.005 0.005 0.0030.003

最意外的发现：-O1 的汇编里已经出现 movabsq $100000000000000, %rdx——sum 被常量折叠了，但循环本身被降级成空转计数器留了下来：

# -O1 生成的 main 片段
        call    clock
        movl    $10000000, %eax
        .p2align 3
.L2:
        subq    $1, %rax
        jne     .L2
        call    clock

而 -O2/-O3 连空循环也删了，两次 clock() 紧挨在一起，测量值落到计时分辨率以下，故按指南要求标注无法可靠区分（也不能为了让计时"有数"而加 volatile，那会改变本实验要观察的优化条件）。其余三点补充：文件大小不能用来看优化效果——PE 节对齐把几十字节的差异掩盖了，改用 size 读代码段才看得出 -O0 → -O1 的一次性收益（11 420 → 11 324，之后不再变化）；用 gcc -Q --help=optimizers 统计各档位打开的优化器数量为 51 / 93 / 142 / 155，说明 -O1 → -O2 增加的 49 个开关里大部分与向量化前置分析有关；终端 time 两个版本 real 几乎相同（0.68 s / 0.69 s），几乎全花在进程创建上，与 11 ms 的循环无关——两种计时测的根本不是同一段时间。

4.4 实验 4：预处理宏

终端实录 4-3　-DDEBUG 控制条件编译
$ gcc -O0 test.c -o test_off.exe && ./test_off.exe
answer = 42
$ gcc -O0 -DDEBUG test.c -o test_on.exe && ./test_on.exe
[DEBUG] x = 42
answer = 42
$ strings test_off.exe | grep -c "\[DEBUG\]"
0
$ strings test_on.exe | grep -c "\[DEBUG\]"
1

strings 给了硬证据：不定义 DEBUG 时调试字符串根本不存在于可执行文件里，不是"运行时被跳过"而是"编译时就没生成"，零开销。-DDEBUG 与 -g 完全不等价：前者是预处理阶段的文本开关，决定哪些代码进入编译；后者只附加元数据，不改变一行机器码。可以同时用，也可以只用其一。

5.5 最长匹配与等长规则优先级

Flex 的选择规则可精确写成两句：最长匹配优先（在所有能匹配当前位置的规则中选文本最长的，与书写顺序无关）；等长时取靠前者。自测反例是 intx：若实现采用"先试关键字、成功即返回"，会切成 KW: int + ID: x；实际输出 ID: intx，证明最长匹配在所有规则间统一比较。另一方向的反例是 int 本身：它无法用长度区分，只能靠顺序——这就是所有 C 风格词法分析器都把关键字规则写在标识符之前的原因。

5.6 从正规式到自动机

终端实录 5-5　生成文件中的自动机结构
$ grep -n "yy_accept\[" lex.yy.c | head -2

696:            if ( yy_accept[yy_current_state] )

正规式先转成 NFA，多条规则合并后再确定化为 DFA，最后压成转移表与接受表；yy_accept[state] 给出"到达该状态时接受哪条规则"，第 696 行的判断是"若当前状态是接受态就记下来，以便继续试更长的匹配"。最长匹配在实现上就是不断前进，把最近一次遇到的接受态记下来，走到不能再走时回退到该位置。这也解释了 5.3 节的设计：0|[1-9][0-9]* 让自动机读完 0 之后对"下一位是数字"不再有接受路径，不会与 OCT 造出两个等长接受态。具体构造算法（Thompson 构造、子集化）在项目 2 中学习。

第 6 章　思政融合：国产编译器调研

6.1 调研对象

本次调研选择华为毕昇编译器（BiSheng Compiler）。按 openEuler 软件包仓库的官方描述，它是"华为编译器实验室针对鲲鹏等通用处理器架构场景，打造的一款高性能、高可信及易扩展的编译器工具链"[1]。选择它的理由很直接：它是国内少数已进入主流 Linux 发行版软件源、能被普通用户 yum install 下来直接使用的自研编译器，而非停留在发布会上的概念产品。

6.2 关键发现

支持语言与前端组成。毕昇不自己发明语言，而是复用 LLVM 生态：C/C++ 交由 Clang 完成词法、语法、语义分析与 LLVM IR 生成并兼任驱动，Fortran 交由 Flang（由 flang1 与 flang2 两个组件构成）[1]。这与第 2 章看到的 GCC 结构形成对照：GCC 的 cc1 是高度集成的单体程序，LLVM 系前端则按库拆分。

目标架构。官方文档把"架构"一栏写死为 AArch64，软件源路径为 repo.oepkgs.net/bisheng/aarch64/[1]——它的定位不是通用跨平台编译器，而是面向 ARM 服务器、特别是鲲鹏处理器的深度定制。鲲鹏社区的文章印证了这条路线：面向 x86 迁移到鲲鹏的场景，华为提供毕昇编译器、毕昇 JDK、GCC for openEuler 三件套，分别对应高性能计算、Java 业务与通用场景[2]。

工具链组成。编译 C/C++ 用 clang/clang++，Fortran 用 flang；链接默认调系统 ld，可用 -fuse-ld=lld 换成 LLVM 的 lld[1]——编译器与链接器解耦，与第 3.6 节 -### 看到的 collect2 → ld 是同一套分工。openEuler 已把它收进官方源，yum install bisheng-compiler 即装。

一项有来源支持的技术特征。官方表述为："除 LLVM 通用功能和优化外，毕昇编译器的工具链对中端及后端的关键技术点进行了深度优化，并集成 Auto-tuner 特性支持编译器自动调优"[1]。两个可核查点：优化发生在中端（IR 层）与后端（目标代码层），与第 4 章观察到的 -O1 常量折叠、-O2 死代码消除属同一层级；Auto-tuner 靠反复编译、运行基准并测量来自动搜索编译参数，本质上是把第 4 章"按场景选选项"那张表交给机器迭代。性能方面，鲲鹏社区口径为 SPEC CPU 2017 相比开源 GCC 9.3 提升约 25%[2]——这是厂商公布的测法，不宜直接外推到自己手上的程序。

6.3 我的思考

做完项目 1 再看毕昇，最直接的感受是"四阶段"是跨编译器的通用语言：clang -E/-S/-c 与 GCC 同名选项语义一致，因为二者都是"驱动 + 前端 + 优化器 + 后端 + 汇编器 + 链接器"的结构。第 3 章学到的观察方法——-E 看宏展开、-S 看指令、nm 看符号、objdump -r 看重定位——换任何一款类 LLVM 编译器都仍然有效。工具会换，方法论不会。

差异背后的原因更值得记。GCC 的 cc1 是单体可执行文件，Clang 是库化的：libclang 可被 IDE、静态分析器直接调用，这是 LLVM 生态在工具化方向扩张快的原因，也解释了国产编译器为何普遍选"基于 LLVM 深度定制"而非"从零写一个 GCC"——站在成熟的开源基础设施上做增量创新，是更现实的技术路线。局限同样清楚：架构绑定 AArch64，x86 开发机用不了；依赖系统已有的 GCC（≥4.8.5）、glibc（≥2.17）、libstdc++（≥6）[1]，并非自包含工具链；Auto-tuner 靠反复编译测量收敛，更适合发布前的最终构建而非日常开发。

关于"一次可复现体验"，我设计了如下验证方案（本机为 x86_64 Windows，无法直接执行）：在 openEuler AArch64 上安装毕昇后，对同一份 hello.c 分别执行 clang -E/-S/-c，与本次 GCC 的三份产物并排比较——预期 .i 行标记格式、.s 伪指令（GCC 用 .seh_*）、.o 节名与符号修饰会有差异，但四个阶段的划分、nm 中 T/U 的含义、重定位项应当一致。若一致，即证明"四阶段"是工具链层面的客观结构，而非某一家编译器的实现细节。编译器为什么是基础软件，第 4 章也给了具象答案：同一段循环 -O0 下 11 ms、-O2 下被彻底消除——编译器不动一行源码，就决定了程序的性能上限；把尺度放大到一座超算集群，这个差距就是电费与机时。

第 7 章　综合反思

7.1 最有趣的环节

-O1 已经把 sum 折叠成常量，却留下了执行 1000 万次的空计数循环（4.1 节），于是"算术都不做了，计时还有 3 毫秒"。它推翻了"优化等级是单调滑杆"的直觉——真实情况是一组彼此独立的变换，各自有不同触发条件：常量折叠 -O1 就做，死循环消除要等 -O2。-O1 的"半优化状态"最需要警惕：既丢了可调试性，又没拿到性能。

7.2 最大收获

"编译"从一个词变成了一条流水线：五样文件、四个阶段、符号解析与重定位两个机制。三条最实用的经验——出错先判断错在哪个阶段（语法错带行列号发生在编译期，undefined reference 报的是目标文件名，发生在链接期）；-### 是理解工具链最快的入口；能交给正规式表达的歧义，不要留给规则顺序兜底（DEC 写成 0|[1-9][0-9]* 而非 [0-9]+，把"075 算 DEC 还是 OCT"在源头消除）。

7.3 还存在的疑问

一是为什么 -O2 的可执行文件反而比 -O0 大 36 字节——代码段明明更小，推测与 PE 节对齐和导入表布局有关，尚未逐节比对；二是 clock() 在 Windows 上的实际分辨率与时钟源，-O0 九次采样从 0.008 s 波动到 0.017 s，跨度接近一倍，需要确认是否受 CPU 频率调节影响；三是 Flex 生成文件里 yy_accept[20] 只有 20 项而规则状态显然更多，说明状态经过重映射与压缩，等价类合并的细节留待项目 2；四是第 6 章设计的毕昇验证方案尚缺 AArch64 实机执行。方法上的一点体会：凡是"预期"与"实测"不一致的地方都原样记录（PE32+ 与 ELF、WinMain 与 main），这些差异恰好说明四阶段是抽象结构，格式与命名只是实现细节。
